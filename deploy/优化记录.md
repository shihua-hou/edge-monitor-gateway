# 长线优化记录

每条都写清楚**改了什么**、**为什么**、**怎么验证**。按批次组织，一批是一个
完整可验证的单元，方便你逐批确认而不是面对一大堆散装改动。

## 批次 1：传感器健康状态（跨四端）

### 问题

所有传感器的失败值都伪装成合法读数：

| 传感器 | 读取失败时的表现 |
|--------|------------------|
| DHT11 温湿度 | 保留上一次的值 |
| HC-SR04 超声波 | 返回 0（看着像"贴着障碍物"） |
| MPU6050 姿态 | 三个角度清 0（0° 恰是最不可疑的姿态） |
| 光敏 ADC | 转换超时时读到上次的残留值 |

结果：线松了、模块坏了，大屏上照样是一个稳定的数字，没有任何人会发现。
**对监控系统来说，"以为在看数据、其实在看一具尸体"比直接报错严重得多。**

还有两个衍生问题：

1. DHT11 的动态阈值在"40 位全相同"时失效——阈值落在数据自身上，全判成 0，
   而全 0 的校验和恰好也是 0，**能通过校验**，上报 0℃/0% 的假读数。
2. 阈值告警会拿陈旧值反复触发。传感器恰好在 41℃ 时坏掉，之后永远重复报
   "温度过高"，而真实温度早降下来了——一条永不消失的假告警比没有告警更糟。

### 改动

**固件（`firmware_stm32/`，已同步到 `EdgeMonitor_App/`）**

- `app_task.h`：`SensorData_t` 新增 `sensor_health` 字节 + `SENS_FAULT_*` 位定义。
  单独占一个字节而不是并进 `sys_state`——后者由 cmd 任务写，健康位由 collect
  任务写，挤在一起就是两个任务对同一地址做读-改-写，会互相覆盖。
- `app_task.c`：四路传感器各自的"连续失败计数"，达到阈值才置故障位
  （温湿度 3s / 超声波 1s / 光敏 1s / IMU 0.5s），成功立即清除。
  健康字节放进 CAN `0x101` 的 `data[6]`（原来是填 0 的保留字节）。
  另：`OnCanRx` 里的 `Cmd_t` 改为清零初始化，之前会把中断栈残留数据入队。
- `sensor/mpu6050.c/.h`：`MPU6050_GetAngle` 改为返回状态码；读失败时**保持
  上次角度**而不是清零。
- `sensor/adc_light.c/.h`：初始化失败不再 `while(1)` 死等（那会导致最高优先级
  任务卡死 → 看门狗复位 → 再次卡死的**无限重启循环**，串口上什么都看不到）；
  改为标记外设不可用、返回错误码。同时补上 `HAL_ADC_PollForConversion` 的
  返回值检查——超时时 `GetValue` 读到的是上次残留值。
- `sensor/dht11.c`：脉宽极差检查。0 位标称 26~28us、1 位标称 70us，正常数据
  极差必然超过两倍；极差过小说明这批脉宽没有区分度，判为读取失败。

**网关（`gateway_imx6ull/gateway_mqtt.c`）**

- 解析 `0x101` 的 `data[6]`，作为 `hf` 字段并入 `monitor/<dev>/data/imu`。

**Web（`web/`）**

- `app.js`：`applySensorHealth()` 维护健康位；`setGauge()` 支持 `stale` 状态；
  故障位**变化时**才告警（否则每帧刷一条，几秒就淹没告警列表）；
  阈值告警跳过已失联的传感器。
- `index.html`：`.dv-gauge-ring.stale` 虚线灰边样式 + `.stale-tag` 文字标记。
  刻意不用红色——红色在这套界面里代表"数值超阈值"，而失联是另一回事：
  数据本身不可信，不是数据超标。

**Qt 中控（`imx6ull_ui/`）**

- `dashboardpage.cpp/.h`：`updateSensorHealth()`，失联的数值变灰并追加"失联"。
- `attitudewidget.cpp/.h`：`setStale()`，IMU 失联时水平仪盖半透明蒙版 +
  "姿态传感器失联"。姿态仪表尤其需要——地平线停住不动跟"车停着"看起来一样。
- `mainwindow.cpp/.h`：缓存 `hf` 并转发；阈值告警同样跳过失联传感器。

### 怎么验证

1. **拔掉 DHT11 的数据线**（或 MPU6050 的 SDA），3 秒内：
   - Web 仪表盘对应的环变成虚线灰圈，数值下方出现"已失联"
   - 告警中心出现一条"温湿度传感器失联"
   - 6U 屏幕上对应数值变灰并显示"失联"；拔 IMU 时水平仪盖上蒙版
2. **插回去**：故障标记应在 1 秒内消失，并出现一条"已恢复"。
3. **回归**：正常状态下 `hf` 恒为 0，界面表现与改动前完全一致。

## 批次 2：板子网络自愈 + 自动校时（`deploy/sysvinit/edgemonitor-daemon.sh`）

### 问题

现场真实故障：随身 WiFi 挂久了之后，板子在 AP 的设备列表里还显示"已连接"，
二层也还能跟同网段的机器通信，但**到网关的转发已经失效**——ping 网关 100%
丢包、ARP 表里网关是全 0。`wpa_supplicant` 自己察觉不到，因为关联状态是好的。
只有重新走一遍认证握手才能恢复。

另外板子没有 `ntpd`，RTC 存的是本地时间却被系统当 UTC 读，**时刻快 8 小时**。
这会让讯飞这类云服务的鉴权签名超出有效窗口，报 401——**看起来完全像密钥填错**。

### 改动

- `export TZ=CST-8`，日志时间戳和 `date` 输出恢复正常。
- `network_watchdog()`：每 60s 探测一次网关，连续失败 3 次（约 3 分钟）触发
  自动重连；两次重连间至少间隔 5 分钟，防止 AP 真的关机时反复折腾。
- `wifi_reconnect()`：完整的降/升接口 + 重新关联流程。**必须放在守护脚本里**
  ——重连过程中 WiFi 会断，在 SSH 里手动跑的话命令自己会被 SIGHUP 打断在
  半路，板子从此彻底失联。守护脚本是 `setsid` 脱离终端跑的，不受影响。
- `sync_time_http()`：首次联网成功后用 HTTP 响应头的 `Date` 校时，
  `hwclock -w -u` 落盘。用 `nc` 手写 HTTP/1.0 请求而不是 `wget`——busybox 的
  wget 没有 `-S`，拿不到响应头；用 1.0 是因为 1.1 长连接会让 `nc` 一直挂着。
- 探测成功/校时失败都有日志。**成功才打日志、失败悄无声息**是排查时最要命的
  组合——看不到日志你分不清"没跑"和"跑了但失败"。

### 怎么验证

- 启动后约 1 分钟，`/tmp/em_daemon.log` 出现"网络自愈已启用"和"校时完成"。
- `date` 显示北京时间，`date -u` 比它早 8 小时（两行都对才算好）。
- 断开随身 WiFi 约 3 分钟，日志出现探测失败计数并自动重连。

## 批次 3：讯飞语音鉴权（已联调通过）

### 三个不同根因，报的都是 401

| 根因 | 修复 |
|------|------|
| 板子时钟快 8 小时，签名超出 5 分钟窗口 | 校时 + 时区（见批次 2） |
| base64 里的 `+` 在 URL 查询串中被解成空格 | `xfyunauth.cpp` 改用 `QUrl::toPercentEncoding` + `StrictMode` |
| APISecret 手抄错了两个字符（`J`/`j`、`l`/`I`） | 从控制台复制 |

星火大模型另有两个问题：Path 用了废弃的 `/v2/chat/completions`（403），
Domain 填 `x2` 不在服务端白名单里（业务错误码，正则是 `^((?i)spark-x|x1|asean)$`）。
现已改为 `/x2` + `spark-x`。

### 关键的可观测性改动

- `xfyunauth.cpp` 增加 `[xfyun] sign date=...` 日志——**它把"时间"这个变量从
  401 里摘了出去**，剩下的才好一个个排除。这是整件事真正的转折点。
- `mainwindow.cpp` 的 `assistantError` 同时写 stderr。之前错误原话只存在于
  屏幕横幅（几秒就消失）和聊天气泡里，日志一个字都没有。

### 时序 bug

`voiceassistant.cpp` 里三处 `emit 信号` 和 `teardownSocket()` 的顺序反了。
`teardown` 才会把状态机复位成 Idle，而接收信号的槽几乎一定会紧接着发起下一个
语音任务（听写结果→送大模型，大模型回复→朗读），那些入口第一句就是
`if (m_mode != Idle) 报错返回`。表现为**链路上每一环都正常，唯独整条链走不通**，
报"正在进行其它语音任务"。

## 批次 4：触摸虚拟键盘（`imx6ull_ui/virtualkeyboard.cpp/.h`）

板子内核 4.1.15 没编 `uinput` 模块，"从网页注入按键到 /dev/input"这条路走不通；
Qt 官方的 `qtvirtualkeyboard` 模块 NXP 的 SDK 里也不带。所以自己写了一个：
一堆 `QPushButton` + 往焦点控件发 `QKeyEvent`，零额外依赖。

两个关键设计：

- 所有键帽 `Qt::NoFocus`。这是整个类能成立的前提——按钮默认会在点击时抢走
  焦点，那样"当前焦点控件"就变成键帽自己，按键发给谁都不对。
- 键盘是**布局成员**而不是浮层。弹出时上面的内容被自然压扁，聊天页输入框
  跟着上移、设置页滚动区缩短，不会出现"正在输入的框被键盘盖住"。

键帽文字全部用中文/ASCII，不用 `⇧ ⌫ ↵`——板子字体集不带这些字形，会显示成
方块（导航栏图标当初就踩过这个坑）。

## 批次 5：600px 屏高的布局溢出（`imx6ull_ui/`）

语音助手页底部的输入框和麦克风按钮被切掉一半。原因：布局的**最小高度超出
屏幕约 32px**。`QMainWindow` 全屏时若布局最小尺寸大于屏幕，Qt 不会压缩内容，
而是让窗口比屏幕更大，底部直接被切在屏幕外。

- `chatpage.cpp`：边距 9→4、间距 10→6；输入框最小高 46→40；
  **滚动区最小高度显式设为 0**（关键：聊天记录区是这页唯一该让步的部分，
  屏幕不够高时缩的应该是它，而不是把输入框挤出屏幕；软键盘要占两百多像素，
  没这一行弹出时会重演同样的问题）。
- `micbutton.cpp`：56→48（仍高于触摸舒适下限 44）。
- `mainwindow.cpp`：内容区上下边距 16→8、间距 10→8。

## 批次 6：Web 缓存（`web/index.html`）

后端是 `python3 -m http.server`，只发 `Last-Modified`、不发 `Cache-Control`，
浏览器按启发式规则自作主张地缓存——改完文件传上去、刷新却还是旧界面，
很容易误判成"文件没传上去"。

- 加 `Cache-Control: no-cache` 等三个 `<meta>`。
- `app.js` 改为动态插入 `app.js?t=<时间戳>`。`<meta>` 只管 HTML 文档本身，
  管不到子资源，光有 meta 会出现"页面是新的、逻辑还是旧的"这种更难查的状态。

## 批次 7：OTA 按设备隔离（`gateway_imx6ull/ota_service.c` + `web/app.js`）

### 问题

数据和控制 topic 早就按设备拆开了，唯独 OTA 还在用全局的 `monitor/ota/cmd`。
这不只是"不统一"：多台机器人接同一个 broker 时，网页上给 A 车点"开始升级"，
B 车的 `ota_service` 同样收得到，**所有车一起进入升级流程**——而升级会让
STM32 复位并擦写 Flash，是最不能"顺带波及"的操作。

进度和结果同理：两台车同时升级时，进度条会互相覆盖，网页上看到的是两条流
混在一起的乱序数字。

### 改动

- topic 改为 `monitor/<dev>/ota/{cmd,progress,status}`，`<dev>` 取自 `DEVICE_ID`。
- Web 端订阅/发布跟着当前选中设备走，`switchDevice()` 里一并退订旧的、订阅新的。
- 路由判断从 `topic === 'monitor/ota/xxx'` 改成先看 `/ota/` 再看后缀。

> **这个改动必须两边同时部署**，只更新一边会导致 OTA 完全不通。

## 批次 8：Web 展示层的防御与空状态

### 数值防御（`web/app.js`）

`onStatusData` 里直接写 `data.t.toFixed(1)`：只要某一帧的 `t` 缺失或是 null 就抛
`TypeError`。而这个函数后面还要更新 LED/蜂鸣器状态、推曲线、判告警——异常一抛
整段就断在中间。现象是"仪表盘突然不动了"，控制台里一行报错，页面上毫无提示，
很容易被当成设备离线。

加了 `num()` 做统一收敛，`status` / `imu` / `motor` 三个分支都走它。
顺带把光照和距离四舍五入——网关目前发的是整数，但万一改成平均值，
界面上会直接冒出 `66.72537654233024` 这种一长串小数（实测复现过）。

### 空状态（`web/index.html` + `app.js`）

"还没有数据"是这套界面上出现频率最高的状态之一（没接 GPS、设备离线、
还没产生告警），却一直是最没设计过的地方：

- 视频那个 `<img>` 没有 `src` 时，浏览器画的是**碎图图标**——那是"页面出错了"
  的通用信号，而这里其实一切正常，只是没设备。
- 地图面板是一整片纯黑加一行小字。
- 事件时间轴是一行居中的"暂无事件"。

统一成 `.dv-empty` 组件：**图标 + 一句状态 + 一句解释**，让人一眼看出是没数据
而不是坏了。地图下方那行重复的"等待 GPS 定位…"也去掉了。

### 历史图的状态提示（`web/app.js`）

原来无论"正在加载""服务连不上""这段时间确实没数据"，画布上一律写"暂无历史
数据"。最要命的是第二种：明明是服务没起来，却告诉用户"没有数据"，把人往
"是不是设备当时没在线"的错误方向带。现在按 `histState` 显示对应的提示和排查建议。

## 批次 9：偏航角溢出（`firmware_stm32/sensor/mpu6050.c` + `web/app.js`）

### 问题

偏航角是陀螺仪积分出来的，没有磁力计校正，会一直朝一个方向漂：

```c
s_yaw += gyr_yaw;                    // 一直累加，从不归一化
*yaw_x100 = (s16)(s_yaw * 100.0f);   // s16 量程只到 ±327.67
```

漂过 327.67° 时**整数溢出翻转**，数值从 +327 直接跳到 -327。曲线上是一条贯穿
全图的垂直线，看着像"车瞬间掉了个头"。**这是必然发生的，只是早晚问题。**

### 改动

- 固件里归一化到 `(-180, 180]`。用 `while` 而不是 `fmodf`：20ms 一帧最多转几度，
  最多循环一两次，比取模便宜，也不用担心负数取模的实现差异。
- 图表侧给偏航序列加 `wrap:true`：相邻两点差超过半个量程时**断开**分段画。
  归一化之后，正常转向经过 ±180° 仍会有一次跳变，那是真实的角度变化——
  断开比画一条假的连线诚实，曲线本来就不连续。

## 批次 10：命令闭环确认（`web/` + `firmware_stm32/app_task.c`）

### 问题

点一下"LED 开"，界面立刻变成"开"——但那只是**乐观更新**，它证明的仅仅是
"消息发出去了"。真实链路是：

```
浏览器 → MQTT broker → 网关 → CAN → STM32 → 状态帧 → 一路回来
```

中间任何一环断了（网关挂了、CAN 没接、STM32 正在复位），界面照样显示"已开"，
而灯根本没亮。对远程控制系统来说这是最不能接受的一类错觉：**操作者以为自己
控制住了设备，其实没有。**

### 改动

- 控制页新增「命令回执」面板：等设备把状态位回传回来才判定成功，并量出整条
  链路的**往返时延**（那个数字本身也是诊断信息——平时一百多毫秒，突然涨到
  两秒就说明链路上有东西堵了）。
- 四种状态：`等待回执` / `已确认 xxx ms` / `未生效` / `已发送（无状态回读）`。
  最后一种是诚实标注：转向和调速反映不到状态位上，只能确认"发出去了"。
  假装确认比不确认更糟。
- **超时判定用独立定时器，不依赖数据帧驱动**。第一版写在"收到下一帧状态"里
  检查，实测发现设备离线时压根不会再有帧过来——而那正是这个功能最该抓住的
  场景，命令会永远停在"等待回执"，看起来像还在路上，实际上石沉大海。
  判超时的逻辑不能依赖被判定对象还活着。
- 固件配套修复：`sys_state` 的 bit2（电机）原来只置位、从不清零，按过一次
  "前进"之后就永远是 1。状态位如果只会置位、永不复位，它表达的就不是"状态"
  而是"曾经发生过"，对操作者是误导。现在停止命令会清掉它。

## 批次 11：视觉一致性（`web/index.html` + `app.js`）

- **密码框是白底的**。样式选择器里只写了 `input[type=text]` 和 `[type=number]`，
  漏了 `password`，于是设置页的 APISecret 和登录页的密码框用的是浏览器默认样式——
  在这套深色界面里就是一个刺眼的白框。顺带补了 Chrome 自动填充的覆盖
  （它用 `!important` 强行盖背景色，只能用超长内阴影 + `-webkit-text-fill-color` 治）。
- **告警等级的 emoji 换成自绘圆点**。🔴🟡🟢 在不同系统上是不同字体、不同造型
  （Windows 扁平、macOS 立体、Linux 上可能没有），带光泽的彩色小球放在这套
  扁平的技术界面里很跳戏，尺寸也不受 CSS 控制。改成 `box-shadow` 做光晕的
  圆点，跟大屏那边的 `.dv-alert-mini .dot` 是同一套视觉语言。
- `info` 等级之前没有对应的类名，"设备上线"这类事件显示成一个没有颜色的灰点，
  看着像等级未知而不是"这是一条正常信息"。

## 批次 12：常驻服务的健壮性

### `gateway_imx6ull/screen_share.c`

1. **只 read 一次就当整个 HTTP 头收完了**。TCP 是字节流，没有"一个 read 对应
   一个请求"这回事，请求头完全可能被拆成两个报文。局域网上小请求通常一次就到，
   所以平时看不出问题——这正是它讨厌的地方：一个依赖时序的偶发失败，上传大
   文件时触发概率明显升高，表现为莫名其妙的"HTTP 头不完整"，重试一次又好了。
   改成循环读到 `\r\n\r\n` 为止。
2. **没有 socket 超时**。连上却不发数据的客户端会让线程永远阻塞在 `read()` 上，
   线程是 detach 的、数量没有上限，几个卡住的连接就是几个再也回收不了的线程。
   半开连接（对端拔网线/断电）尤其常见——TCP 不会主动告诉你对面没了。
   加了 10 秒的 `SO_RCVTIMEO` / `SO_SNDTIMEO`。

### `server/history_logger.py`

1. **开启 WAL 模式**。默认的 rollback journal 下一次写入会阻塞所有读——前端拉
   6 小时曲线（几千行）的同时正好有数据落库，两边就互相等。WAL 下读的是快照，
   写不挡读，正好匹配"一个写线程 + 若干 HTTP 读线程"的访问模式。
   配 `synchronous=NORMAL` + `busy_timeout=5000`。
2. **`_insert` 没有异常兜底**。它是从 MQTT 回调线程里调的，抛出去之后 paho 只会
   打一行堆栈然后继续跑——数据没写进去，而那行堆栈混在正常输出里很容易被忽略，
   表现为"历史曲线莫名其妙缺了一段"。现在捕获并限流打印（每 30 秒一条，
   既不淹没日志也不会让问题彻底无声）。
3. **`VACUUM` 无条件执行**。它是把整个库重写一遍、期间锁住数据库，没删掉任何
   东西时做这件事纯属白白卡住一次写入窗口。改成只在真的删了行之后才做。
4. **单实例锁**。它用的是固定的 client_id `history_logger`，跑两份会互相踢下线，
   日志上看是"连上、断开、连上、断开"反复刷，而两个进程都"在运行"——非常难
   往"跑了两份"这个方向想（网关那边踩过一次）。用 `flock` 而不是 PID 文件：
   进程被 `kill -9` 时 PID 文件会留下变成陈旧的锁，flock 由内核自动释放。

## 批次 13：CAN 链路自愈（`gateway_imx6ull/gateway_mqtt.c`）

### 问题

`can_thread` 读失败时直接 `break`，线程悄悄退出。之后进程还活着、MQTT 还连着、
网页上设备显示"在线"，**只是永远不再有数据上来**——从外面看跟"传感器坏了"
一模一样，是最误导人的一种状态。

而 CAN 控制器进入 bus-off（干扰、线松了、对端掉电都会导致）后**不会自己恢复**，
必须把接口 down 一次再 up，控制器才会重新初始化。既然故障是可恢复的，
就不该让它变成永久失效。

### 改动

- `can_recover()`：`ip link set canX down` → `up type can bitrate 500000`。
- 读失败后自动恢复并重开 socket，成功即继续；失败按 2/4/8…60 秒指数退避重试。
- **fd 置换顺序**：先把 `g_can_fd` 置 -1，再关闭本地保存的旧 fd。反过来的话，
  `close` 之后到置 -1 之前有个窗口——若 mosquitto 重连恰在这一瞬拿到同一个 fd
  号（内核总分配最小空闲号，很容易撞上），下行命令线程就会**把 CAN 帧写进
  MQTT 的 TCP 连接里**。概率极低但后果是协议流被污染，只能靠写对顺序避免。
- `on_message` 下发前检查 `g_can_fd < 0`，恢复期间明确提示"命令已丢弃"，
  而不是让 `write(-1)` 报一个语义完全不同的"总线接线有问题"。
- 恢复中断言：`g_can_fd < 0` 时直接跳到恢复流程，不去 `read(-1)`——否则日志里
  会冒出 "Bad file descriptor"，看着像新故障，其实只是还没恢复。

## 批次 14：日志治理

### `imx6ull_ui/mqttclient.cpp`

`onLogCb` 把 mosquitto 的**每一条**日志都写 stderr，包括 DEBUG 级的
"Client xxx received PUBLISH"。传感器每秒推 5 帧 = 日志每秒 5 行。

**这个噪声真的害过一次**：排查讯飞鉴权失败时 `tail -25` 翻上去全是 PUBLISH，
真正的错误一条都看不见。日志的作用是让问题浮出来，不是把问题埋进去。

现在只放行 `MOSQ_LOG_WARNING | MOSQ_LOG_ERR`。需要看完整 MQTT 交互时注释掉
那一行即可。

### `deploy/sysvinit/edgemonitor-daemon.sh` 日志轮转

`/tmp` 在这块板子上是 **tmpfs——写进去的日志占的是内存**。几个常驻进程各写一份，
跑几天能把内存吃掉一大块，最后表现成"系统变慢/进程被 OOM 干掉"，
而没人会想到是日志撑的。

超过 512KB 就截断保留后一半。两个坑都绕开了：

1. 不能 `tail -c N f > f`——重定向先把 f 截成 0 字节，tail 读到空文件，日志全丢。
2. **中转完不能用 `mv` 覆盖**。日志正被子进程通过 `>>` 持有 fd，而 `mv` 换的是
   inode：进程手里的 fd 仍指向旧 inode，之后所有输出都写进那个已经没有文件名的
   旧文件——新日志永远是空的，旧 inode 又因为还被打开而不会释放，内存一点没省，
   反而把日志弄丢了。典型的"轮转之后日志就不动了"。
   正确做法是 `cat tmp > f`：截断的是**同一个 inode**，以 `O_APPEND` 打开的
   写入方仍然接着往新末尾写。

## 批次 15：视频服务的拒绝服务隐患（`gateway_imx6ull/video_v4l2.c`）

`accept()` 之后**立刻同步 `read()` 请求行**，带 5 秒读超时。问题在于这是个
单线程 select 循环：一个连上却不发数据的客户端（半开连接、扫端口的、网络中途
卡住的）会把整个循环堵死 5 秒，期间**所有正在观看的客户端一帧都收不到**。
一个坏连接拖垮全部观看者，是无意间造出来的拒绝服务。

改成"待鉴权表"：accept 只登记，等 select 说它可读了再读，读操作永远不阻塞
主循环；一直不说话的连接由 5 秒超时统一回收。待鉴权的 fd 跟 `clients[]`
分开存放——它们还没通过 token 校验，绝不能收到视频帧。

## 批次 20：不让"少一个功能"变成"整机变砖"（Bootloader + 天气客户端）

### `firmware_stm32/bootloader/boot_main.c`（及 `EdgeMonitor_Boot/User/main.c`）

`Boot_CAN_Init()` 里三处 HAL 失败都是 `while (1);`。**CAN 初始化失败 = 设备
永久卡在 Boot 里，App 永远起不来**——而 App 的采集、屏幕、串口跟 CAN 好不好
没有任何关系，完全可以正常跑。

现场看到的就是一块通电后只打了一行 Boot 横幅、之后什么都不做的板子，
而真实原因只是"CAN 外设没起来，不能通过总线升级"。

**把"少一个功能"升级成"整机变砖"，是错误处理里最不该犯的错。**

改动：`Boot_CAN_Init` 返回状态码，失败时打印原因并**直接去启动 App**，
跳过 3 秒握手等待（没有 CAN 就没有升级这条路，白等没意义）。
只有"App 也无效 + CAN 也死了"才真的停下来。
`Boot_CAN_Send/Recv` 加 `s_can_ok` 保护作为防御。

> 这两个文件是 `sync_firmware.py` 的 EXEMPT 条目（开头注释和 include 路径
> 不同），不会自动同步，**两份都改了**，改完 diff 过代码部分完全一致。

### `imx6ull_ui/weatherclient.cpp`

没有超时。`QNetworkRequest::setTransferTimeout` 是 Qt 5.15 才有的，而嵌入式
SDK 常年停在 5.9/5.12，用不了。

网络半死不活时（TCP 连着但没有任何响应——**正是 WiFi 关联僵死时的典型状态**），
reply 永远不会 `finished`：天气永远停在上一次的值上，既不更新也不报错；
而 refresh 每半小时来一次，pending 的 reply 只增不减。
**"永远等待"是最坏的一种失败——它连"失败了"这个信息都不给你。**

改动：自己挂一个 10 秒的 `QTimer::singleShot` 去 `abort()`。
用 `QPointer` 而不是裸指针——reply 正常完成时会 `deleteLater`，
定时器晚一步触发的话裸指针就是野指针。
abort 造成的错误单独措辞（"10 秒无响应"），否则界面上显示的是
"Operation canceled"，看着像谁取消了操作。

## 批次 21：OTA 上位机的两处隐患（`gateway_imx6ull/uds_tool.c`）

### 一、固件大小上限是过时的常量

```c
if (fsize <= 0 || fsize > 64 * 1024) {          /* ← 写死 64KB */
    fprintf(stderr, "firmware size %ld invalid (0~64KB)\n", fsize);
```

而 A/B 分区**每个槽是 240KB**（`fw_meta.h` 的 `SLOT_SIZE`）。当前固件约 62KB，
**刚好卡在这个上限边缘**没暴露出来。App 再加点功能超过 64KB，OTA 就会拒绝
升级，还报一句 "size invalid"——让人以为是固件文件坏了，实际上文件完全正常，
只是这行常量过时了。

**这类"今天恰好没事、明天必然出事"的硬编码比直接的 bug 更难查**：出问题时
你改动的是别处（加了个功能），没人会想到回头看这一行。

改成 `SLOT_SIZE_BYTES (240 * 1024L)`，并在注释里写明它必须跟 `fw_meta.h`
保持一致（不 include 那个头文件是因为它带一堆 STM32 HAL 依赖，为一个常量
把它拉进上位机工具不划算）。

Boot 侧（`uds.c:375`）本来就用的 `SLOT_SIZE`，是对的，不用改。

### 二、0x27 种子响应没校验长度就取值

```c
rc = do_req(s, "0x27 请求种子", req, 2, resp, &rlen);
if (rc) goto fail;
uint32_t seed = ((uint32_t)resp[2] << 24) | ... | resp[5];   /* ← 没查 rlen */
```

`do_req` 只保证"收到了肯定响应"，不保证长度。DLC 短一点的话这里就在读
`resp` 数组里从没被写过的部分（栈上的残留），算出来的密钥自然对不上——
而报错会停在**下一步**的"0x27 发送密钥失败"上，把人往"密钥算法写错了"
的方向带，实际原因是上一步的响应就不完整。

加了 `rlen < 6` 的检查和明确的错误信息。

## 批次 23：超声波驱动的同类问题（`firmware_stm32/sensor/hcsr04.c`）

跟 `adc_light.c` 完全一样的模式：`HC_SR04_Init()` 里两处 HAL 失败是 `while (1);`。
这个函数在**最高优先级的采集任务**里调用，卡住 = 整机停摆 = 4 秒后被看门狗
复位 = 重启后再次卡在同一行，**无限重启循环**，串口上一个字都没有。

改成返回状态码 + 标记 `s_tim_ready`，失败时 `GetDistance` 恒返回 0（等同无回波），
由采集任务置 `SENS_FAULT_DIST` 故障位。`GetDistance` 开头也加了就绪判断——
不判的话会去读一个未初始化的定时器计数值，超时判断随之失效，最坏情况是
`while` 循环永远出不去，反而把任务锁死。

顺带确认了两件事：

- `s_echo_flag` / `s_t1` / `s_t2` **已经是 `volatile`**（ISR 和任务共享）。
  这个如果漏了，`-O2` 下编译器可能把 `while (s_echo_flag != 2)` 里的读操作
  提到循环外，变成死循环——是这类驱动最经典的坑，这里没踩。
- `GetDistance` 里 `const u16 TIMEOUT_US` 的声明必须在所有语句之前：
  ARMCC 默认按 C90 编，"声明后面才允许出现语句"是硬性的。第一版补的就绪
  判断插在了声明前面，会编不过，已调整顺序。

## 批次 24：守护脚本自身的三个缺陷（真机重启暴露）

这三个都是"部署到真实环境"才暴露出来的，写代码时想不到。

### 一、`is_running()` 用了不带 `-ef` 的 `ps`

这块板子上的 `ps` 是 procps 风格：**不带参数时只列出"和调用者同一个控制终端"
的进程**。而守护脚本是 `setsid` 起的、根本没有控制终端。

`deploy/README` 里我自己写过"busybox 的 ps 要带 -ef"，脚本里却漏了。

更要命的是**排查命令也踩了同一个坑**：清理多余守护进程用的
`ps | grep edgemonitor-daemon | awk '{print $1}' | xargs kill` 一个都没杀掉，
于是每执行一次"清理+重启"就多叠一个实例，最后同时跑了 **4 个**。
而 `ps | grep -c "程序名"` 返回 0 又让我误判成"系统全挂了"，
实际上五个程序一直好好跑着。

**一个用错的诊断命令，能同时制造出一个真问题和一个假问题。**

### 二、守护脚本没有单实例保护

网关和历史服务都加了 flock，唯独这个"管着所有程序"的脚本没加——结果最容易
叠起来的偏偏是它。

多实例的实际危害不是浪费 CPU，而是**网络自愈会互相打架**：网关一旦不通，
N 个实例会同时 kill `wpa_supplicant` 并重连 WiFi，彼此把对方的重连过程打断，
本来能恢复的网络反而彻底起不来。

加了 flock（fd 9 持有），第二次启动会被明确拦下并提示怎么处理。

### 三、开机自启从来就没配过

`/etc/rc.local` 里什么都没有。**板子断一次电，整套系统就再也起不来**——
以前每次都是手动 `setsid` 拉起的，只是板子连续跑了两天半没重启，
所以这个最基本的缺陷一直没暴露。

对一个"园区巡检机器人"来说，这比之前修的所有问题都更要紧。

已加进 `rc.local`（插在 `exit 0` 之前，原文件备份为 `rc.local.bak`）。
同时注释掉了厂家自带的 `/opt/QDesktop`——它也画 framebuffer，
和 Qt 界面同时跑会抢同一个 `/dev/fb0`。

### 重启实测结果


**顺带确认了一件之前不知道的事**：这块板子开机根本没有任何东西负责启 WiFi
（重启后 `wlan0` 接口都不存在），是网络自愈把它拉起来的。这个功能本来是为
"WiFi 关联僵死"设计的，结果第一次真正派上用场是在开机场景。

### 四、开机恢复太慢（本批次一并改掉）

上面日志里 WiFi 用了 **3 分钟**才起来——因为按常规逻辑要"连续 3 次失败才动手"。
但开机时网络没起来是**预期内的常态，不是故障**，不该走完整的故障确认流程。

改成：开机后第 3 轮（约 30 秒）先探一次，不通就立刻拉 WiFi；
之后才进入"连续 3 次失败才重连"的常规节奏。
开机恢复从 3 分钟缩到约 30 秒，而运行期间的偶发丢包仍然不会触发误重连。

顺带修了日志措辞：原来接口不存在时打印的是"网络探测失败（第 1 次，网关 ）"
——括号里空着，看着像日志本身出了问题。现在区分"无默认路由"和"网关 x.x.x.x 不通"。

## 批次 25：自愈逻辑亲手弄断了网络（真实事故复盘）

**这是整个项目里我犯过的最严重的错误，值得完整记下来。**

### 现象

给守护脚本换新版后，板子彻底失联。串口上看日志：

```
11:20:50 开机后网络未就绪，立即拉起 WiFi（开机阶段不等三次确认）
11:20:50 网络自愈：开始重连 WiFi
/home/root/edgemonitor-daemon.sh: line 106: ip: command not found
/home/root/edgemonitor-daemon.sh: line 117: wpa_supplicant: command not found
/home/root/edgemonitor-daemon.sh: line 119: udhcpc: command not found
11:21:02 网络自愈：重连完成，地址            ← "完成"了，地址是空的
11:21:33 网络探测失败（第 1/3 次，无默认路由）
...每 5 分钟重复一次，永远回不来
```

### 根因：PATH

用 `setsid` 从 SSH 的**非登录 shell** 启动脚本时，继承到的 PATH 只有
`/usr/bin:/bin`，没有 `/sbin` 和 `/usr/sbin`。于是：

- `ip route` 找不到 → `net_ok` 永远判定"无默认路由" → **网络其实好好的，坏的是探测本身**
- 触发自愈 → `killall` 恰好在 `/usr/bin` 里，**能找到** → wpa_supplicant 被杀
- `ip` / `wpa_supplicant` / `udhcpc` 全都找不到 → **没有任何东西被拉起来**
- 网络断了，且每轮重复，无法自行恢复

开机走 `rc.local` 时反而一切正常——因为那里有 `source /etc/profile`。
**同一个脚本，换个启动方式行为就完全不同。**

### 三条修复，对应三个教训

**① 守护进程绝不继承 PATH**

脚本开头写死 `PATH=/sbin:/usr/sbin:/bin:/usr/bin:...`。
常驻进程的运行环境必须自己确定，不能依赖"谁启动了我"。

**② 拆之前先确认装得回去**

`wifi_reconnect()` 现在会先检查 `ip`/`wpa_supplicant`/`udhcpc`/`killall`
是否都在，缺一个就直接放弃，**不做任何破坏性操作**。

> 拆到一半发现工具不在手边，比一开始就不动更糟——
> 不动至少还留着一个能用的系统。

这条适用于所有"先拆后装"的恢复流程，不只是网络。

**③ "ping 不通"不等于"网络没就绪"**

原来的开机判据只看 ping 结果。而这个随身 WiFi 的 ICMP 本来就时好时坏
（排查它时就见过），单次丢包就去断网重连，是拿一个能用的网络去冒险。

改成看**网卡有没有配上地址**（有没有 IP、有没有默认路由）——那才是
"确实没就绪"。有地址只是丢包的情况，交给常规的"连续三次失败 + 5 分钟
冷却"流程慢慢确认，代价可控。

### 更根本的一条

**自愈逻辑本身就是高风险代码。** 它在系统已经不正常时执行破坏性操作，
判断依据一旦出错，就会把"有点小毛病"的系统变成"彻底不可用"。

这个功能是今天加的，而它造成的停机比它修复的问题还多。

所以自愈的门槛应该定得比"看起来不对劲"**高得多**，并且必须遵守：

- 判据要用**结构性事实**（有没有 IP、有没有路由），不用**观测结果**（ping 通不通）
- 动手前验证**恢复手段可用**
- 破坏性操作要有**冷却时间**和**次数上限**
- 每一步都要留日志，尤其是"我决定不动手"这种情况

### 附带确认

顺带验证了上一批的 `9>&-` 修复确实生效：守护进程被 kill 之后，
锁文件已无人持有（此前是被它派生的 gateway_mqtt / wpa_supplicant 等一直攥着）。

## 批次 26：Qt 字体环境（跟 PATH 同一个病根）

部署完新的 Qt 界面后，远程抓屏发现：**布局和矢量图标都在，但所有文字都不见了**，
面板全是空框。

原因跟批次 25 的 PATH 一模一样：`/etc/profile` 里定义了三个 Qt 变量

```sh
export QT_QPA_FONTDIR=/usr/share/fonts/ttf
export QT_QPA_PLATFORM=linuxfb:tty=/dev/fb0
export QT_QPA_FB_TSLIB=1
```

开机走 `rc.local` 时因为那里有 `source /etc/profile` 才正常；用 `setsid`
从 SSH 启动守护脚本时一个都没有，Qt 找不到字体目录。

**这个现象比"程序起不来"难查得多**：进程在跑、日志没报错、屏幕也亮着，
只有真正看一眼屏幕才会发现不对。日志里其实有一行
`QFontDatabase: Cannot find font directory`，但它混在启动信息里毫不起眼。

守护脚本现在自己设这三个变量，并照抄了 `/etc/profile` 里那个
"某些屏（fbset timings 第三列 220/213）要 unset tslib"的判断。

### 归纳：守护进程的环境必须自给自足

两次事故指向同一条：

| 依赖项 | 缺失时的表现 |
|--------|-------------|
| PATH（`/sbin`、`/usr/sbin`） | 网络探测永远失败 → 自愈把网卡拆了又装不回去 |
| QT_QPA_FONTDIR | 界面一个字都没有，但毫无报错 |

共同点是**同一个脚本换个启动方式行为就完全不同**，而且失败得很安静。
常驻服务不能假设自己是从登录 shell 启动的——systemd 时代这是常识
（`Environment=` / `EnvironmentFile=`），手写 sysvinit 守护脚本时特别容易忘。

**验证方法也值得记**：光看进程列表和日志会得出"一切正常"的结论，
是远程抓一帧屏幕才发现文字全没了。**对带界面的程序，最终验证必须看画面。**

## 批次 27：视频服务被我改成了"每个正常连接都拖垮所有人"

### 我原本要修的问题

`video_v4l2.c` 是单线程 `select` 循环。原来 `accept()` 之后立刻同步 `read()`
请求行（带 5 秒读超时）——一个连上却不发数据的客户端（半开连接、扫端口的、
网络中途卡住的）会把整个循环堵死 5 秒，期间所有正在观看的人一帧都收不到。
**一个坏连接拖垮全部观看者**，是无意间造出来的拒绝服务。

改成：`accept` 后只登记进"待鉴权表"，等 `select` 说它可读了再读。

### 我引入的问题（更严重）

连接通过鉴权、被放进 `clients[]` 之后，**同一轮循环紧接着就走到"检测断开"分支**，
而那个 fd 在 `rfds` 里仍然是置位的（正是因为它可读才被处理，数据已被读走）。
于是对一个没有数据的 socket 做**阻塞 `read()`**，整个服务冻住。

结果：**每一个正常连接都会拖垮所有人**——比原来的问题严重得多。
现象是浏览器一连上，所有观看者（包括新连接）什么都收不到，
日志里只见 `client joined` 紧跟着 `client left`。

### 还有一层：卡死之后连 kill 都不管用

`killall`（SIGTERM）杀不掉它。信号处理函数把 `g_running` 置 0，但主循环卡在
`read()` 里回不到检查点，而信号多半带 `SA_RESTART`，`read()` 被自动重启——
**进程卡到连正常终止都做不到**。必须 `kill -9`。

排查时这一点很有迷惑性：`killall` + 等守护脚本重启，`ps` 一看进程"在"，
就以为新版已经生效了；实际上跑的还是卡死的旧进程（对比启动时间才发现）。

### 修复

1. 加入 `clients[]` 后立刻 `FD_CLR(c, &rfds)`——这个 fd 的可读标志已经被消费了。
2. "检测断开"的探测读改用 `recv(..., MSG_DONTWAIT)`。
   **探测性读取本身就不该有阻塞的可能**：`select` 的可读标志随时可能是过期的
   （同一轮里被别的分支消费掉就会这样），不能指望调用方永远记得清标志位。

### 教训

- **`select` 的就绪标志是一次性的**。同一轮里被消费之后，后续分支再据此做
  阻塞 I/O 就是错的。多个分支共用一个 `fd_set` 时尤其容易踩。
- **探测性 I/O 一律用非阻塞**，不要依赖"理论上这里有数据"。
- **验证"新版本是否生效"不能只看进程在不在**，要对比启动时间——
  尤其是当旧进程可能卡死到杀不掉的时候。
- 这条改动的初衷是提升健壮性，结果引入了更严重的可用性问题。
  **改动本身也是风险**，尤其是这种"看起来只是重构了一下 I/O 时序"的改动。

## 批次 28：HOME 没设，密钥"重启后就丢了"（同源第三例）

### 现象

重启后语音助手报「语音助手未配置讯飞 APPID/APIKey/APISecret」，
而配置文件明明好好地在 `/home/root/.config/EdgeMonitor/edgemonitor_ui.conf` 里，
三个值一个不少。

### 根因

UI 进程的 **`HOME=/`**。

`QSettings` 把配置存在 `$HOME/.config/<组织>/<应用>.conf`——HOME 不同就是
两个完全不同的文件。开机由 `rc.local -> init` 启动时 HOME 是 `/`，
UI 去 `/.config/` 找，读到一片空白。

而手动从 SSH 重启守护脚本时一切正常，因为 SSH 会话的 `HOME=/home/root`。

### 这是同一个病根的第三次

| 缺失的环境变量 | 后果 | 手动启动时 |
|---|---|---|
| `PATH`（缺 `/sbin`） | 自愈把网卡拆了装不回去，断网 20 分钟 | 正常 |
| `QT_QPA_FONTDIR` | 界面一个字都没有，无任何报错 | 正常 |
| `HOME` | 读不到自己存的密钥，报"未配置" | 正常 |

**三次的共同点是"手动测都好、开机就坏"。** 而最自然的验证方式——
ssh 进去手动启动一下看看——恰好绕开了问题，这才是它们难查的真正原因。

### 结论

守护脚本现在把 `PATH` / `HOME` / `QT_QPA_*` 全部显式写死，
并用 `env -i`（完全空的环境）启动验证过：子进程拿到的环境仍然正确。

**常驻服务的运行环境必须自给自足。** systemd 时代这是常识
（`Environment=` / `EnvironmentFile=`），手写 sysvinit 守护脚本时特别容易忘——
因为开发期永远是从有环境的 shell 里启动的。

## 附：语音链路的远程验证方法（人不在现场时）

用户不在板子旁边，没法判断"喇叭到底响没响"。用摄像头自带的麦克风做
**声学回环**，客观定量地回答了这个问题：

**1) 放 1kHz 纯音，对录音做 Goertzel（只看单一频点）**

| | 1000Hz | 对照 700Hz | 对照 1500Hz | 比值 |
|---|---|---|---|---|
| 不放音 | 1.8 | 2.2 | 1.8 | 0.9 |
| 放纯音 | **452.0** | 3.2 | 0.3 | **256 倍**（≈48 dB） |

→ **喇叭、功放、音频输出通路全部正常。**

**2) 但整体电平只抬高了 2.6 dB**

说明麦克风（在摄像头上）到喇叭的声学耦合很弱。
TTS 语音比纯音低 13 dB，按同比例只能抬高约 0.15 dB——实测 0.3 dB，对得上。
所以"TTS 录不到"不代表没响，只代表这个麦克风太远/太钝。

**3) 混音器还有余量**：Speaker 110/127（-11 dB），数字通道已满、无额外衰减。

**方法本身值得记**：单频点检测（Goertzel）能在信噪比很差的录音里
把信号挖出来，而宽带语音做不到——因为噪声是摊在所有频点上的，
而纯音的能量集中在一个点。远程验证音频输出时，**测纯音而不是测语音**。

## 批次 29：又一轮系统性查错

这轮把之前没细看的几个文件过了一遍。先说**没找到问题的**——这同样是结论：

| 文件 | 检查项 | 结果 |
|------|--------|------|
| `imx6ull_ui/mqttclient.cpp` | 跨线程回调、payload 生命周期、析构顺序 | 干净。回调统一用 `QueuedConnection` 投递、payload 就地深拷贝、析构里先 `loop_stop(force)` 再 `destroy` |
| `gateway_imx6ull/gps_mqtt.c` | NMEA 字符串解析越界 | 干净。字段数 `n < 16` 有界，`strncpy` + 显式截断 |
| `gateway_imx6ull/screen_share.c` | 网络传入的触摸坐标 | 干净。`clamp_xy()` 钳到屏幕范围 |
| `server/history_logger.py` | SQL 注入 | 干净。`metric` 走白名单决定表名/列名，其余全是绑定参数 |
| `bootloader/uds.c` 的 `do_transfer` | 写 Flash 越界 | 干净。同时校验槽末尾和固件总长度 |

### 找到的三个问题

**① `MAX_FIRMWARE` 还是 64KB（`bootloader/boot_uds.h`）**

跟批次 21 在 `uds_tool.c` 里修掉的是同一个过时常量——**而我当时只改了上位机一侧**。

这让情况比原来更糟：上位机放行 240KB、设备端在 64KB 拒绝，报出来的是 0x34 的
UDS 否定响应，工具那边显示成"请求下载失败"，比原来那句 "size invalid" 更难定位。

**改协议的一侧而不改另一侧，本身就是一个 bug。** 已改成 `SLOT_SIZE`，
两边注释都写明了对应关系。

> ⚠️ Boot 区的改动要 **J-Link 重刷 Bootloader** 才生效，OTA 升不了 Boot 自己。
> 当前固件 33KB，离 64KB 还有距离，所以是"已入库、未部署"状态。

**② `do_transfer` 的 `nb` 没有钳位**

`nb = len - 2`，CAN 帧最长 8 字节所以现在不会超 `BLOCK_LEN`。但 `s_dl_received`
是按 `nb` 累加的，哪天这个函数被别的传输层（串口/网络）复用而帧更长，
计数就会虚高，"已接收 == 总长度"提前成立，**固件传了一半就被当成传完**。
拷贝循环本身有上界，不存在内存安全问题，这里防的是计数错乱。

**③ `?limit=-1` 能把整张表拖出来（`server/history_logger.py`）**

```python
limit = min(int(one("limit", "2000")), 20000)   # 只挡了上界
```

SQLite 里 **`LIMIT -1` 的语义是"不限制"**。实测 `?limit=-1` 返回了 **14466 个点**，
按 30 天保留算能到几十万行——服务端要在内存里拼一个巨大的 JSON。

改成 `clamp_int()` 夹在 `[lo, hi]` 内，参数非法时返回 **400** 而不是让 `int()`
抛异常走到最外层 except 变成 **500**（那会让人以为是服务端崩了）。

### 一点观察

这轮找到的三个问题里，有两个是**"今天恰好没事"的过时常量/缺失下界**——
它们的共同点是：**当前输入恰好落在安全区间内**，所以测试永远测不出来。
这类问题只能靠读代码发现，不能靠跑。

## 批次 30：Qt 界面的两个长期运行问题

### ① 告警横幅：第二条开始只显示 0.2 秒（`notificationbanner.cpp`）

`dismissCurrent()` 为了"收起动画放完再显示下一条"，把 `QPropertyAnimation::finished`
接到了 `showNext` 上。**那条连接在进入 `showNext` 之后依然挂着** ——
于是【展开】动画一结束（220ms）又触发一次 `showNext`，把队列里下一条立刻顶上来。

后果：**多条告警排队时，从第二条起每条只显示 0.2 秒**，根本来不及看。
而告警恰恰是成批来的——传感器失联、阈值超标、命令未生效可能在同一秒内
全部触发，**最需要看清的时候反而看不清**。

根子在于"一次性的回调用了持久连接"。修复是在 `showNext()` 启动展开动画前
显式 `disconnect`，让节奏完全由 `m_dismissTimer` 控制。

### ② 聊天气泡只增不删（`chatpage.cpp`）

每条消息（包括每条错误提示）都 `insertWidget` 一组 Qt 对象，从不移除。

桌面程序上无所谓，但这是一台要连续跑几周的设备：

- 内存无上限增长
- **更早暴露的是"卡"**：`QVBoxLayout` 每次插入都要重算全部子项，
  条数一多，每发一句话的开销线性上升，用得越久界面越迟钝
- 出错时增长最快：网络断了的话，每条命令都会追加一条错误气泡

加了 60 条上限（远超一屏能显示的量），超出就从头部删最旧的。
用 `deleteLater` 而不是 `delete`——这个函数是在消息回调链里被调到的，
被删的部件可能正处在 Qt 的事件派发路径上。

### 顺带确认没问题的

- `controlpage.cpp` 的命令回执逻辑（独立定时器判超时、无状态位的动作
  诚实标注"已发送"）——正确，且 `mainwindow.cpp:319` 确实接上了 `onStateBits`
- `mainwindow.cpp` 的换页淡入动画：`QPropertyAnimation` 对目标持 `QPointer`，
  快速切页不会踩到已删除的 `QGraphicsOpacityEffect`

### 这一批的共同点

两个都是**"单次操作看不出、长期运行才显形"**的问题：
一条告警时横幅完全正常，聊几句时气泡也完全正常。
它们只在**连续使用**下暴露——而嵌入式设备的正常状态恰恰就是连续运行几周。

## 批次 31：`gateway_can.c` 的负数打印（当前就是错的）

```c
printf("俯仰:%d.%02d° 横滚:%d.%02d°", pitch/100, pitch%100, roll/100, roll%100);
```

C 的整数除法和取模**对负数都向零取整**：

| 真实值 | 变量 | 打出来 |
|--------|------|--------|
| -125.33° | `roll = -12533` | `-125.-33°` |
| -0.5℃ | `temp = -5` | `0.-5℃` ← **符号整个丢了** |

这块板子的横滚常年在 -125° 左右，**这个诊断工具的输出一直是错的**，
只是没人细看。温度那个更隐蔽：零下且绝对值小于 1℃ 时，负号会彻底消失，
在户外巡检场景（冬天）是常态。

改成 `%.1f` / `%.2f` 配 `/10.0`、`/100.0`。实跑验证：

```
[0x101] 俯仰:0.61° 横滚:-125.16° 偏航:-124.01°     ← 修复后
```

### 同一个文件里另外三处

- **`struct ifreq` / `struct sockaddr_can` 没有 memset**。`gateway_mqtt.c` 里
  专门修过这个问题并写了注释，这个文件当时漏了。`ifreq` 是 union，ioctl 只填
  `ifr_ifindex`，其余字节是栈上的垃圾并被传进内核；`strncpy` 在源串刚好占满
  `IFNAMSIZ-1` 时也不补结束符。
- **`read()` 出错后直接 `continue`**：接口被 down 掉时 `ENETDOWN` 会持续返回，
  变成 100% CPU 的忙循环并刷屏。改成区分 `EINTR`、其余错误歇 1 秒。
  这是诊断工具，**故意不做自动恢复**——接口没了就该让人看见。
- **`send_ctrl` 未使用**导致 `-Wall` 永久告警。留一个永远会告警的函数，
  久了会让人对告警整体麻木——**而告警一旦被习惯性忽略，就不再有价值**。
  加 `__attribute__((unused))` 并说明它为什么留着。

### 一个差点被我改错的地方（`firmware_stm32/can.c`）

`CAN1_SendStd` 等待发送完成用的是**裸循环计数**：

```c
u16 timeout = 0;
while (HAL_CAN_IsTxMessagePending(&hcan1, mailbox)) {
    if (++timeout > 0xFFF) { abort; return 0; }
}
```

这正是 `hcsr04.c` 里明确避免过、还写了注释的做法（超时时长跟主频/优化等级
绑死）。我准备把它改成基于 `HAL_GetTick` 的时间判据，先去确认 tick 走不走——

**工程里有两个 `SysTick_Handler`：**

```c
/* User/stm32f1xx_it.c:145 */
#if (!SYS_SUPPORT_OS)            /* SYS_SUPPORT_OS=1，这份被编译掉了 */
void SysTick_Handler(void) { HAL_IncTick(); }
#endif

/* Drivers/SYSTEM/delay/delay.c:44  ← 实际生效的是这份 */
void SysTick_Handler(void) {
    HAL_IncTick();
    if (调度器已启动) xPortSysTickHandler();
}
```

**只看 `stm32f1xx_it.c` 会得出"HAL 的 tick 是死的"这个相反结论**，我差点就
照着这个错误前提做决定。

确认 tick 能用之后，反而决定**不改**，理由是风险不对等：

- `HAL_GetTick` 分辨率 1ms，而一帧 8 字节 CAN 报文在 500kbps 下只要 0.22ms。
  基于它的超时至少得给 2~3ms，比现在（约 0.8ms）还长，对发送路径更不利。
- 这段代码跑在周期上报任务里。超时判据一旦失效变成死循环，结果是
  看门狗复位 → 重启 → 再次死循环，而 A/B 的 pending 早已确认过、**不会回滚**
  ——就是一块无限重启的砖。
- 换来的只是"理论上更可移植"。

已把这整段推理写进代码注释，包括"两个 SysTick_Handler"这个陷阱，
以及真要改时正确的做法（用自由运行的硬件定时器，像 `hcsr04.c` 那样）。

**不改也是一种决定，但必须把"为什么不改"留下来**——否则下一个人会重新
推一遍，而且很可能推错。

## 批次 35：超声波"传感器坏了"其实是 PB6 浮空

**现象**：`hf` 健康位长期是 `2`（SENS_FAULT_DIST），距离恒为 0。换了一个全新的
HC-SR04 之后，依然没反应——两个模块都坏的概率很低，说明之前"传感器硬件故障"
这个结论下早了。

**定位手段**：加了一个 `HC_SR04_SelfTest()`，**完全绕开 TIM4 输入捕获**，纯 GPIO
轮询读 ECHO，把故障切成四类分别打印。这一步是关键——原来的代码路径里，
"模块没响应"和"输入捕获没工作"两种完全不同的故障，表现出来都是"距离=0"。

**两轮结果**：
1. 第一轮 `ECHO never falls`：ECHO 有上升沿但 40ms 内不下降。这排除了没供电／
   TRIG 没接上（那样根本不会有上升沿）。
2. 把 PB6 从 `GPIO_NOPULL` 改成 `GPIO_PULLDOWN`，第二轮直接 `width=2420us
   dist=41cm`，连续 5 次稳定。

**根因**：PB6 配的是浮空输入。ECHO 那条线接触不良时，浮空脚被旁边 TRIG 的
10us 跳变**容性耦合**拱成高电平，然后没有任何东西拉它回来，就一直悬在高位。
表现出来像"模块卡死"，实际是线没接好。真正的回波不管有没有障碍物都会在几十
毫秒内落下来。

**为什么下拉要长期保留**（不只是排障手段）：模块是推挽输出，内部下拉约 40kΩ，
接好时对信号毫无影响；但它能让"线掉了"这种故障**老实表现为"没有回波"**，从而
被 `health_update` 正确记成 `SENS_FAULT_DIST`。这条直接关系到 `hf` 健康位的可信
度——**故障要能被如实上报，前提是故障不能伪装成别的样子**。浮空脚把"断线"
伪装成了"模块卡死"，健康位虽然也置了位，但把人引向了换硬件这条错路。

**教训**：这个 bug 让我误判了一次，还让用户白买了一个传感器。所有**外部输入
引脚都不该配浮空**——浮空的代价不是"读数不准"，而是"故障会说谎"。

**顺带修的工具问题**：这次改代码时 `

` 又被 Bash heredoc 吃成真换行，
Keil 报了 21 个 missing closing quote。给 `scripts/brace_check.py` 补了「断串」
检查：用状态机扫（区分代码／行注释／块注释／字符串／字符），能正确跳过
`"https://"` 这种串里带 `//` 的情况，56 个文件 0 误报，注入错误能定位到行号。
括号平衡和可疑痕迹两项旧检查都拦不住这类错——它们括号是平的。

**待验证**：自检走的是裸轮询，**正式测距走 TIM4 输入捕获，还没验过**。
下次开机后看 Web 大屏的「距离」，或 `mosquitto_sub -t 'monitor/robot01/data/status'`
的 `d` 字段：不为 0 且随手的远近变化、同时 `hf` 的 bit1(0x02) 消失，才算真通。

## 批次 36：VM 换 IP 引出的桥接 ARP 陷阱

**触发**：路由器（移动随身 WiFi）重新分配，VM 从 .6 变成 .4，板子的
`/etc/edgemonitor.env` 里 `MQTT_HOST` 写死的是 .6，整条链路断了。

### 三个独立问题，一层套一层

**① 配置改了但进程不认。**
守护脚本每轮巡检重读 `/etc/edgemonitor.env`，注释里写着"改完最多等一个巡检
周期就生效"——**这句话只对还没启动的进程成立**。`gateway_mqtt` 在 `main()` 里
`getenv("MQTT_HOST")` 读一次就存下来，之后重连循环一直朝旧地址打。
必须 `killall` 让守护脚本重新拉起才会捡到新地址。

**② 静态 IP 也救不了：桥接在 WiFi 上会做 MAC 转换。**
给 VM 配了静态 192.168.100.240 之后，板子依然 ping 不通。看板子的 ARP 表：

```
192.168.100.240  ->  2c:9c:58:c3:f1:03   （宿主机 PC 的 MAC）
192.168.100.7    ->  2c:9c:58:c3:f1:03   （同一个）
```

VMware 把 ens33 桥接到宿主机的 **WiFi 网卡**，而 WiFi station 只能用一个 MAC，
所以 VM 的流量对外全顶着宿主机的 MAC。后果是这个 IP->MAC 映射**只有在 VM
主动发过包之后才存在**，而且 30 秒（`base_reachable_time_ms`）就老化。

方向性正好和业务相反：**MQTT 是板子主动连 VM**。映射一掉，板子 ARP 不到 VM，
就永远连不上——而 VM 那边 ping 板子却是通的，呈现出诡异的单向可达。
让 VM 主动 ping 一次板子，板子立刻就通了（21ms）。

**处置**：VM 上加用户级 cron（不需要 sudo），每 15 秒 ping 一次板子，把映射焐着。
这是治标。**根治方案是 VM 改 NAT + 宿主机端口转发**，让板子去连 PC 的地址——
PC 是真实 WiFi station，永远 ARP 得到，不存在这个问题。已记入待办。

### 我在这一轮犯的错

**看到旧数据就宣布"数据通了"。** 查 SQLite 时只看了几行温湿度光照，没核
时间戳，直接说链路恢复了。实际那批数据是 **26 小时前**的，最新一行停在
09-07 09:27——正是 VM 关机的时刻。基于这个错误前提，我进一步推出"超声波的
输入捕获路径有问题"，还让用户去烧一版打寄存器的调试固件。

**真相是超声波早就好了。** 修完 PB6 下拉、板子重新上报之后，`dist` 一直是
50~57cm 的正常读数，TIM4 输入捕获从头到尾没毛病。那版调试固件完全是白费的。

教训：**查时序数据必须先看时间戳**。一张只有数值没有时间的表，看起来和实时
数据毫无区别——而"数据存在"和"数据是新的"是两回事。这条对监控系统本身也
成立：大屏上的数字如果不带新鲜度标记，故障时会安静地显示最后一个正常值。
（项目里已经有 `isStale()` / `stale-tag` 做这件事，这次是我自己查库时没守这条规矩。）

## 批次 37：地址收敛成一处 + 板子 CA 证书过期

### 一、broker 地址：三处收敛成一处

今天断链的根因不是 IP 变了，是**同一个地址存在三个地方**，改一处漏两处：

### 二、板子 CA 证书 7 年没更新，天气一直连不上

现象：Qt 报 `SSL handshake failed`。这个报错**指错了方向**——听起来像 TLS 协议
或密码套件不兼容，实际握手是成功的。

用 `openssl s_client` 手工握手才看清：

```
New, TLSv1/SSLv3, Cipher is ECDHE-RSA-AES128-GCM-SHA256   ← 握手成功
verify error:num=20:unable to get local issuer certificate ← 验证失败
```

两个问题叠在一起：
1. `/etc/ssl/certs` 里有 174 个 `.pem`，但 **hash 软链是 0 个**。OpenSSL 的
   `-CApath` 靠 `c_rehash` 生成的 hash 软链查找，没有软链这个目录形同虚设。
2. 证书链是 Let's Encrypt 的 `YR2` ← `ISRG Root YR` ← **交叉签名到 `ISRG Root X1`**，
   而板子的 CA 包是 2019 年的，没有 X1。

换成当前的 Mozilla CA 包（curl.se/ca/cacert.pem，2026-08-13）后
`Verify return code: 0 (ok)`，天气立刻出来了（22°C 阴）。
**不需要升级 OpenSSL**——1.0.2h 能沿着服务器送来的交叉证书接回 X1，
前提只是信任库里得有 X1。

装在两处：`/etc/ssl/certs/ca-certificates.crt`（Qt 扫这个目录）和
`/usr/lib/ssl/cert.pem`（OpenSSL 的 OPENSSLDIR 默认 CAfile）。原文件都留了 `.bak`。

教训：**嵌入式板子的根文件系统一旦做好就很少再动，CA 包会随时间静静过期。**
这类故障的信号是"某个 HTTPS 服务突然连不上，而别的都正常"，而应用层给出的
错误信息（"handshake failed"）会把人往协议兼容性上带。遇到就直接
`openssl s_client` 手工握一次，`verify return code` 那一行说的才是实话。

### 三、天气配置

API Host / Key 推到板子的 QSettings，**没有进源码**——这个项目的源码是要给
面试官看的，密钥进了 git 历史就洗不掉了。

### 四、部署与验证

Qt 在 VM 上交叉编译（`. /opt/fsl-imx-x11/4.1.15-2.1.0/environment-setup-...` 之后
`qmake && make`），二进制推到板子。

替换正在运行的可执行文件要用 `mv` 不能用 `cp`：`cp` 会撞 ETXTBSY，而 `rename`
是原子的——旧进程继续用旧 inode，新进程启动时拿到新文件。旧版本留了 `.bak`。

**环境变量优先做了反证验证**：把 QSettings 里的 host 故意改成 `10.99.99.99`，
重启后日志仍是 `[mqtt] connecting to 192.168.100.240:1883` —— env 确实压过了
QSettings，影子配置再也遮蔽不了。验证完把 QSettings 恢复成正确值（手工启动兜底）。

只验证"改完还能用"是不够的，那证明不了优先级；**必须把兜底那一路故意弄坏，
才能证明主路真的在生效**。

## 批次 38：NAT 改造落地 + 天气自动定位

### 一、NAT + 端口转发已生效

不需要改 VMware 网络模式——虚拟机本来就同时挂着桥接(ens33)和 NAT(ens37)两块网卡。
宿主机上加四条 `netsh portproxy` 转发 + 一条防火墙规则即可：

```
板子 192.168.100.3 --> PC 192.168.100.7:{1883,8083,8080,8090} --> VM 192.168.157.134
```

板子只跟 PC 这一个**真实 WiFi station** 通信，PC 的 MAC 是 AP 正经登记过的，
不存在"要先主动发包才可达"的问题。ARP 保活的 cron 已撤除。

`/etc/edgemonitor.env` 的 `MQTT_HOST` 改成 `192.168.100.7`，三个进程重启后
`[mqtt] connected`，数据 2.8 秒前入库。

验证顺序是有讲究的：**先从板子侧确认四个端口通，再改配置**。反过来做的话，
一旦转发没起效，现在好好的链路会先断掉，然后你要同时面对"转发有没有生效"和
"链路为什么断了"两个问题。

### 二、天气改成 IP 自动定位

原来写死 `location=101010100`（北京）。这台是会被搬走的巡检终端，写死城市 ID
在它换了地方之后就是错的，而且**错得很安静**——温度照常显示，只是显示的是
另一个城市的。

实现：`location=auto` 时先 `http://ip-api.com/json/` 拿经纬度，再以
`"经度,纬度"` 查和风。两个请求共用同一套 10 秒超时/错误处理（抽成 `getJson`，
写两遍的下场通常是只在其中一处修了 bug）。

几个刻意的选择：

**用 http 不用 https 查定位。** 这里没有任何敏感数据（就是问"我的公网出口在
哪"），不值得为它引一层 TLS；更重要的是板子的 CA 包刚因为过期把天气整个搞挂
过一次（批次 37），少一个 HTTPS 依赖就少一个会随时间静静烂掉的东西。

**用户显式配了就以用户为准。** 只有 `auto`/空 才自动定位。和这个项目里其它
地方一个原则：显式配置永远压过自动推断。

**城市名必须显示在界面上。** 现在是 `杭州 · 晴` 而不是光一个 `晴`。
因为 IP 定位定的是**公网出口所在地，不是设备所在地**——本项目实测板子走物联网卡
出网，ISP 报的是 "IOT Jiangsu network"（江苏），定位结果却是杭州，出口在运营商
网关上。**不把地名显示出来，定位偏了根本没人能发现。**

这条和超声波那次、ARP 那次是同一个道理：**故障不能伪装成正常**。
一个不带出处的数字，正确和错误长得一模一样。

**不缓存定位结果。** 每次开机重新查一次，一次 HTTP 可以忽略，换来的是设备被
搬走之后天气自己会跟着变——对巡检终端这才是对的行为。

### 三、经度纬度的顺序

和风的 `location` 要 `"经度,纬度"`，**经度在前**，和一般人念的"纬度,经度"
正好相反。写反了会查到地球上另一个地方，而且**照样返回 code=200**，
只是天气不对。代码里专门写了注释。

### 四、手工配位置时也要有城市名

用户指定了南京，于是配成 `location=101190101`。但手工配置这条路原本 `m_city`
是空的，界面就只剩一个温度——又退回到"数字不带出处"。

所以补了 `lookupCityName()`：手工配置时先用 GeoAPI（`/geo/v2/city/lookup`）
反查一次城市名，之后缓存住。反查失败不阻断天气，最多是没地名可显示——
地名是锦上添花，不能因为它拿不到就把主功能也搞没了。

现在两条路径都有出处：自动定位显示 IP 定位给的城市名，手工配置显示 GeoAPI
反查的城市名。

**为什么值得为一个地名多写一个请求**：`101190101` 这种 ID 填错一位照样返回
`code=200`，只是变成了别的城市。没有城市名，这个错永远不会被发现。

### 五、踩到的坑：和风的响应是 gzip 的

用 `wget` / `curl` 手工调 GeoAPI 一直是 `400 Bad Request`，一度以为专属 host
不支持 geo 接口。实际是**和风返回 gzip，命令行不带 `--compressed` 就解不开**。
Qt 的 QNetworkAccessManager 自动处理，所以程序里没这个问题——
**命令行验证失败不等于接口不可用**，工具的差异要先排除掉。

## 批次 39：底盘接入 + OTA 刷新固件 + Qt MQTT 永不重连的 bug

### 一、电机闭环上车

TB6612（WHEELTEC 稳压版 D153C）+ 2×MG513 P28 + 13 线编码器 + Φ65 轮。
引脚全部集中在战舰板 **P2 左排**，12 根线不跨排子。为了做到这一点：
左轮编码器从 TIM3 原生的 PA6/PA7 改成**部分重映射的 PB4/PB5**——既进了 P2，
又避开了 PA5/PA6/PA7 这个挂着 SPI Flash 和 NRF24L01 的雷区（那种冲突极隐蔽：
静止时读数正常，一给电机命令才乱）。代价是 PB5 原来是 LED0，把 `HW_Led_Set`
挪到了一直闲置的 LED1(PE5)。

`__HAL_AFIO_REMAP_SWJ_NOJTAG()` 一次释放 PA15/PB3/PB4 三个脚，正好都要用。

标定：`ENC_CNT_PER_REV = 13 × 4 × 28 = 1456`，`WHEEL_CIRC_MM = 204`。

顺手修了自己写的一个精度 bug：里程原来是 `(计数 / 1456) × 204 / 10`，
**整数除法先除后乘**，不足一圈的部分全丢——里程只能以 20cm 为步长跳变。
改成先乘后除、余数留到下一拍，精度 1mm 且长期不累计误差。

### 二、OTA 刷固件（板子已装车，下载口不方便）

先在代码里把安全链逐环核实过才敢刷：

1. `uds_tool` 发 `0x22 F0 02` 问设备要 A/B 状态，**目标槽由设备自己算**（= 非活动槽），
   升级永远不碰正在运行的固件；
2. `IWDG_Start()` 在调度器启动**之前**就开（4s），`Motor_Init()` 在保护范围内；
3. `App_ConfirmBootOnce()` 要 25 次成功上报（约 5s）才盖章；
4. Boot 试满 `MAX_BOOT_ATTEMPTS = 3` 自动回滚。

最坏情况是重启 3 次回到旧固件，全程不需要下载口。实际一次成功。
**顺带补上了一个挂了很久的待办：重刷 Boot 之后 OTA 依然可用，已验证。**

验证手段是直接 `candump can0,101:7FF` 解 `0x101` 帧：
```
00 21 FE 81 09 4D 00 00
pitch=0.33  roll=-3.83  yaw=23.81  健康位=0x00
```
健康位全 0 → `Motor_Init()` 成功（失败会置 `SENS_FAULT_MOTOR=0x10`）。
`motor_history` 从空表开始有数据，说明 `0x102` 帧在发了。

### 三、Qt 的 MQTT 客户端"一次失败就永久死亡"

**现象**：板子屏幕显示"离线"，但 `gateway_mqtt` 数据照常入库。
同一块板子上两个进程行为不一致——这个反差就是线索。

**根因**（`mqttclient.cpp`）：
```c
int rc = mosquitto_connect_async(...);
if (rc != MOSQ_ERR_SUCCESS) { emit connectionFailed(reason); return false; }
rc = mosquitto_loop_start(m_mosq);   // 永远走不到
```
开机时界面起得比 WiFi 快，`connect_async` 直接返回 `ENETUNREACH`，函数 return，
于是 **`mosquitto_loop_start` 从没被调用——而 mosquitto 的"自动重连"恰恰跑在
loop 线程里**。这个客户端从此是一具尸体，永远显示离线。

讽刺的是紧挨着的注释就写着"loop_start 会另开一个线程做网络收发+自动重连"。
**注释描述的能力是真的，只是那条代码路径永远到不了。**

**修法**：`connect_async` 失败不再放弃，5 秒后重试，无限重试；`loop_start`
加 `m_loopStarted` 守卫只启一次（启起来之后掉线重连由 loop 线程接管）。
间隔用固定 5 秒不用退避：内网设备失败原因几乎总是"网络还没好"，
退避只会拖长恢复时间。

**验证方式**：把 `MQTT_HOST` 临时改成 `no.such.host.invalid`，
日志出现 7 次 `connect_async 失败: Lookup error.（5 秒后重试）`，
证明重试真的在跑；改回正确地址后立刻连上（1883 连接数 2 → 3）。

**只验证"改完还能连"是不够的——那证明不了失败路径。必须把失败故意造出来。**
（同批次 37 验证环境变量优先级时用的是同一个原则。）

## 批次 40：闭环上车调通（附三个真实故障）

板子已经装在车上、下载口不方便，全程走 **OTA** 刷固件，共刷了 4 轮。

### 最终实测

| 命令 | 左 RPM | 右 RPM | 判读 |
|---|---|---|---|
| 前进 20%（目标 40） | +39.0 ± 1.0 | +39.5 ± 1.5 | 稳态误差 ~2%，约 3s 收敛 |
| 后退 20% | −38.1 | −38.2 | 对称 |
| 左转 | −36.5 | +37.4 | 差速正确 |
| 右转 | +34.6 | −34.1 | 差速正确 |

跑了 3.5 米之后，**左右累计里程都是 355cm，误差 0**。方向经肉眼确认为前进。

### 故障一：左轮飞车（负反馈变正反馈）

首测左轮 RPM 一路冲到 **−488**（目标 +40），右轮正常。

**根因不是接错线**，而是这块 WHEELTEC 模块的固有特性：两个电机接口的
**电机极性是镜像的**（`MOTORC2: 1=AOUT1/6=AOUT2`，`MOTORC1: 1=BOUT2/6=BOUT1`），
这样对称安装时同样的 IN1/IN2 能让车直走；**但编码器引脚没有跟着镜像**
（两边都是 `3=ExB, 4=ExA`）。于是两个电机物理反向旋转时，编码器必然输出相反符号。

PI 拿到反相反馈：目标 +40、实测 −55 → 误差 95 → 加大输出 → 更负 → 再加大。
**负反馈变成正反馈，必然发散。**

**定位手段（值得记）**：电机不通电，用手把两个轮子都往车头方向转，看 0x102 的符号。
- 符号相同 → 电机线反了
- 符号相反 → 编码器反相

这两种现象在"飞车"这个表象上完全一样，通电测永远分不出来；**不通电的手转测试
把它们分开了**。修法是加 `ENC_L_SIGN = -1`。

### 故障二：周期性的假尖峰（阻塞式读取污染了控制周期）

0x102 上周期性出现 78 RPM 的尖峰和 4 RPM 的凹陷，**两轮同时**，周期约 23 帧。
轮子不可能真这么跳。

**根因**：`Motor_Tick()` 按**固定 20ms** 算转速，但同一个采集循环里有两个
**阻塞式**读取——超声波每 200ms 等回波（1.8m 约 11ms，无回波最多 35ms）、
DHT11 每 1s 约 25ms。那一拍真实间隔是 31ms 而不是 20ms，编码器多走的计数被
当成"转得更快"，下一拍又偏少。上报周期 200ms 与超声波周期 200ms 缓慢相对
漂移，形成 23 帧的拍频。

这个假尖峰还会**直接灌进 PI 当成巨大误差**。改用 `HAL_GetTick()` 算实际 dt 之后，
RPM 范围从 4~78 收窄到 17~41，尖峰完全消失。

**教训**：只要控制回路和阻塞式 IO 共处一个任务，"周期固定"这个假设就不成立。
要么测实际 dt，要么把控制回路挪到独立任务。

### 故障三：Qt 的 MQTT 客户端一次失败就永久死亡

见批次 39。屏幕显示"离线"而网关数据正常——同一块板子上两个进程行为不一致，
这个反差是定位的起点。

### 新增：飞车保护

任一侧转速超过 `MOTOR_MAX_RPM × 1.5` 并持续 100ms → 拉低 STBY 硬停，
置位 `SENS_FAULT_MOTOR` 上报，**不自动恢复**（要发 `ACT_RESUME`）。

三个设计选择：
- **判据用"转速失控"不用"输出饱和"**：爬坡载重时输出饱和是正常的，转速不会超；
  只有反馈出错时转速才会失控地涨。
- **不自动恢复**：能跑到这步说明反馈链路本身有问题，自动重试只会反复飞车。
- **必须上报**：不上报的话大屏上只看到"转速 0"，和正常停车一模一样，
  **没人会知道刚才失控过**。

### 已知未验证

`ENC_CNT_PER_REV = 13 × 4 × 28 = 1456` 中，减速比 28 已由供应商确认，
但**整体标定未做实测**（手转整圈量里程）。转速和里程可能整体差一个固定比例。
演示够用，做航迹推算前需要补测。

## 批次 41：电池电压监测 + 天气开机竞态（同一个 bug 模式第三次出现）

### 一、电池电压

模块 H2-5(ADC) → PC5(ADC1_CH15)，走板载 100k/10k 分压，12V 进去只有 1.09V。

- `adc_light.c` 扩成 ADC1 的独占持有者，跑两路。**单次转换模式下每次转换前
  重新 ConfigChannel**——不重配的话读到的永远是上一个通道，而那个值看起来完全合理。
- 文件名已经不贴切，但重命名要动 Keil 工程和同步脚本，**调试期间为改名引入
  构建风险不划算**。记作可选清理项。
- 0x101 的 `buf[7]`（一直空着）送 0.1V 单位；一个字节够表达 0~25.5V。
- 网关解析成 `"bat"`，Web 的「系统健康度」加一行，3S 锂电阈值 11.1V 提醒 / 10.5V 危险。

**关键设计：读数 < 3V 判定为"未接入"而不是"电池 0.0V"。**
模块输入范围 4.5~15V，真实电池不可能低于 3V 还在供电；而浮空的 ADC 脚读出来就是 0。
把"没接线"报成"没电了"就是一条永不消失的假告警——**假告警看多了，真告警也就
没人信了，那比没有告警更糟**。

实测：12.1 V，健康位 0x00。

### 二、天气开机后半小时不出来

现象：重启后屏幕显示 `城市名反查失败: Host xxxxxxxxxx.re.qweatherapi.com not found`。

**两个 bug 叠在一起：**

**① 开机竞态 + 重试间隔 30 分钟。** UI 起得比网络快，开机第一次请求必然
DNS 失败，而刷新定时器是 30 分钟。**故障持续几秒，重试间隔半小时——这个比例
本身就是 bug。** 加短重试：30 秒 × 10 次覆盖开机后 5 分钟，之后交回常规刷新。
重试封顶是因为和风免费额度有限，地址填错这种永久性故障不能每 30 秒烧一次配额；
接口返回非 200（key 错、配额用尽）也不重试，那是配置问题，重试没用。

**② 城市名反查失败会把天气整个挡住（我自己写的）。** 那段代码的注释写着
"失败也照常查天气：地名只是锦上添花"，但 `getJson` 的错误分支只是 `return`，
`fetchWeather()` 根本走不到。屏幕上只显示"反查失败"，**完全看不出天气本身
压根没人去请求过**。加 `onFail` 回调真正做降级。

### 三、同一个 bug 模式，这是第三次

| # | 位置 | 表现 |
|---|---|---|
| 1 | `mqttclient.cpp` | `connect_async` 失败 → `loop_start` 没被调用 → **注释里承诺的"自动重连"永远不会发生** |
| 2 | `weatherclient.cpp` | 反查失败 → `return` → **注释里承诺的"照常查天气"永远不会发生** |
| 3 | 天气刷新间隔 | 开机故障持续数秒，重试间隔 30 分钟 |

前两个共性是：**注释描述的是意图，代码路径才是事实。**
写下"失败也会 xxx"的时候，必须确认那条路径真的可达——
最省事的验证方法就是**把失败故意造出来跑一遍**（批次 37/39 都用了这招）。

第三个共性是：**重试间隔必须和故障的时间尺度匹配。**
开机竞态的故障窗口是秒级，用分钟级甚至半小时级的重试去覆盖，等于没修。

## 批次 42：Qt 中控 iOS 化 + RTK 数据通路

### 一、先量清楚这块硬件能承受什么

动手改界面之前先查了平台，两条约束直接决定了设计取舍：

| 约束 | 实测值 | 影响 |
|---|---|---|
| 色深 | `fb0/bits_per_pixel` = **16**（RGB565） | 只有 32 级红/蓝、64 级绿，**大面积微妙渐变会有明显色带** |
| 渲染 | `-platform linuxfb`，单核 Cortex-A7 | 无 GPU 合成，`QGraphicsBlurEffect` 对 1024×600 逐帧模糊跑不动 |

所以：

- **真毛玻璃做不了** → 用"半透明填充 + 顶部 2px 渐变 + 1px 内描边"去仿材质。
  这是诚实的折中：在这块硬件上真模糊的代价是整个界面不可用，而仿出来的
  在 7 寸屏上肉眼几乎分不出。
- **渐变只用在很短的距离上** → 卡片顶部高光只做 2px，其余纯色 + alpha。
- **动画只动小区域** → 见下面第三节。

### 二、squircle：iOS 观感里最容易被忽略的一条

iOS 从 7 开始用的**不是正圆弧**，是连续曲率圆角（continuous corner）——
曲率从直边到圆角是渐变的，而正圆弧在切点处曲率从 0 突跳到 1/r。

单看一个卡片说不清，但整屏十几个圆角一起看，正圆弧会显得"鼓"、有点廉价。
**这是"像素级说不上哪里不对"的主要来源之一。**

Qt 的 `drawRoundedRect` 和 QSS 的 `border-radius` 只有正圆弧，所以
`Ios::squircle()` 用三次贝塞尔手工逼近：控制点伸出量取 `r × 0.72`
（正圆弧的标准常数是 0.5523，调大之后曲率过渡变缓）。这个数是试出来的，
苹果没公开真正的曲线定义。

### 三、动画该动哪里：一条被硬件划出来的界线

原计划做整页滑动转场，算了一下放弃了：1024×600×2B ≈ 1.2MB/帧，
软件 blit 逐帧搬这么多，单核 A7 上必然掉帧。

改成**只动侧边栏的选中滑块**（188×46）。重绘面积差了 250 倍，
而视觉上"选中块滑过去"恰恰是 iPadOS 侧边栏最有辨识度的动作，
整页平移反而不是 iOS 的语言。

**在软件渲染的嵌入式屏上，"动画做在哪"比"动画做得多顺"重要得多。**

弹簧曲线统一用 `OutBack`，overshoot 从默认 1.70 调到 **1.1**——
车机上过冲太大会显得轻浮。

### 四、顺手修掉的两个设计问题

**1. "LED：关"这种按钮文案有歧义。** 到底是"当前是关"还是"点一下就关"？
iOS 用开关表达二态设备正是为了消除这个歧义。改成 `IosSwitch` 后状态一目了然。

**2. 状态回写会触发无限往复。** `setChecked` 会发 `clicked` → 又发一次命令
→ 设备回传 → 又 `setChecked`。加 `blockSignals` 包住。
这是"状态回写类 UI"最常见的坑，不处理的表现是按一次开关命令发个不停。

### 五、一个时序 bug

滑块首次定位用了 `QTimer::singleShot(0)`，结果它停在左上角 (0,0)。

原因：`main.cpp` 里窗口是**开机动画结束后（1.1s）才 `showFullScreen()`** 的，
而构造函数里的 `singleShot(0)` 早就跑完了——那时按钮的 geometry 还是默认值。
改到 `showEvent()` 里再延后一轮事件循环才对。

**"布局算完了没有"这件事，构造函数里永远不知道。**

### 六、RTK 数据通路

`gps_mqtt.c` 重写。修掉一个会让人完全查不到方向的 bug：
旧代码只匹配 `$GPGGA`，而 OEM700（UM982）发的是 **`$GNGGA`**（多星座混合解算），
一条都对不上——现象是"程序在跑、日志干净、就是没数据"。现在只比对后三个字母，
GP/GN/GB/GA/GL 全认。

另外把 `if (fix > 0)` 才发布改成**无解也按 1Hz 发**：
丢星之后地图上会永远停在最后一个点，和"车停在那里"看起来一模一样。

OEM700 的 USB 枚举出 4 个 CDC-ACM 口，分工是实测出来的：
ACM0 静默 / **ACM1 模块日志（LuatOS，也是 Lua REPL）** / ACM2 RTCM 二进制 /
**ACM3 NMEA**。ACM1 的日志直接暴露了 NTRIP 的状态（`wait IP_READY`）。

**待解决（都是硬件）**：天线信噪比偏低（高仰角星只有 29 dBHz，正常应 40~50，
总可见约 10 颗而 UM982 开阔天空应有 30+）；模块 4G 未注册上网，NTRIP 起不来。
