# CAN Bootloader + UDS 设计文档（阶段 9）

> 目标：通过 CAN 总线给 STM32 远程升级固件（OTA），实现禾赛 JD 核心要求的
> Bootloader / UDS / IAP。本设计为"可跑通的实用版"：UDS 服务子集 + 简化传输层，
> 完整 ISO-TP 传输层的扩展方式见文末。

---

## 1. 总体架构

```
Web/命令行上位机          i.MX6ULL 网关                STM32 战舰板
 .bin 文件  ──►  uds_tool  ──CAN(500K)──►  Boot 区(UDS服务+Flash操作)
                  (SocketCAN)                          │
                    │                                   ├─ 写内部 Flash
                    └── 响应/NRC ◄──────────────────────┤
                                                        └─ CRC校验 → 跳转App
```

- **Boot 区**：上电先运行，等待升级握手；无升级则按 A/B 元数据选槽跳转
- **App 区**：拆成 Slot A / Slot B 两个槽，见下面的 A/B 分区说明
- 升级全程走 CAN，无需拆机/调试器——这就是车载 ECU 的 OTA 流程

## 0. A/B 双分区与回滚

**要解决的问题**：只有单个 App 区时，CRC 校验失败能停在 Boot 不刷坏，但新固件
如果**能启动却有 bug**（跑飞、外设初始化失败、逻辑错误），旧固件已经被覆盖，
没有任何退路，只能接 JTAG 重刷。装在巡检小车上的设备出这种情况就得召回。

**Flash 布局**（STM32F103ZET6 共 512KB，页 2KB）：

| 区域 | 地址 | 大小 |
|------|------|------|
| Boot | `0x08000000` | 16KB |
| Slot A | `0x08004000` | 240KB |
| Slot B | `0x08040000` | 240KB |
| Meta | `0x0807C000` | 16KB（只用第一页） |

**采用 direct-xip 模式**（MCUboot 的两种模式之一）：两个槽都能直接执行，
切换只改元数据一个字段，瞬时生效、回滚零成本、没有拷贝窗口。

> **代价：必须编译两份固件。** Cortex-M 代码不是位置无关的，链接到
> `0x08004000` 的固件放到 `0x08040000` 上跑不起来。所以 App 工程要建两个
> Target，分别输出 `xxx_a.bin` / `xxx_b.bin`，`uds_tool` 按设备报告的目标槽
> 自动选对应那份。
>
> （另一种 swap 模式只需一份固件，但要把备份区拷到运行区，拷贝途中断电会毁掉
> 唯一可运行的固件，还得再加一层拷贝恢复逻辑，对这个规模的项目不划算。）

**升级与确认流程**：

```
1. uds_tool 问设备 (0x22 F002) → 得知该写哪个槽（永远是非活动槽）
2. 擦除/写入该槽                 ← 全程不碰正在运行的固件
3. CRC 校验通过 → 该槽标记为 pending，不是直接生效
4. 复位 → Boot 看到 pending，boot_attempts+1 落盘，然后跳过去试
5. App 跑稳（CAN 连续上报 25 次≈5 秒）→ 确认，pending 提升为 active
6. 若新固件跑不起来 → 反复复位，attempts 累加到 3 次 → Boot 自动回滚到旧槽
```

### 实测记录（2026-09-05）

**升级路径**：`0x22 F002` 查到 `target=B` → 工具自动选 `atk_f103_b.bin` →
擦除/传输/CRC 全过 → 复位后 `Trying pending slot B` → App 跑稳 5 秒 →
`A/B: boot confirmed, active slot = B`。**第一次就成功**（吞帧 bug 修复后
不再需要重试）。

**回滚路径**：把 `atk_f103_a.bin` 的前 8 字节（初始 SP + Reset_Handler）
清零后刷入。CRC 校验**通过**——文件本身没损坏，工具算的是文件的 CRC，
这正好说明 CRC 只能证明传输无误、证明不了固件能跑。复位后：

```
Trying pending slot A (attempt 1/3)
Slot A invalid (SP/PC)          ← SlotLooksValid() 当场识破
pending slot unusable, fall back
Boot active slot B
Jump to slot B @0x08040000      ← 立刻回滚，无需耗满三次
EdgeMonitor STM32 Node boot OK
```

向量表明显非法时不必等三次，`SlotLooksValid()` 直接判死。三次计数是留给
另一种情况的：**固件能启动、但跑不到确认那一步**（跑飞/卡死），那种只能
靠反复复位累加计数来发现。

顺带验证了 S3 超时：上位机中途被 `head` 掐断，Boot 进了编程会话后没了下文，
10 秒后自动 `S3 timeout, exit programming session` 退出，没有卡死在解锁状态。

三个容易做错的点：

- **计数必须"先落盘再跳转"**。等启动成功再计数的话，跑飞的固件根本不会执行到
  计数那一步，就永远触发不了回滚。
- **确认时机不能太早**。App 一进 `main` 就确认等于把整套机制废掉——固件哪怕
  启动 200ms 后就跑飞，也已经被盖章为"可用"。必须等核心功能真的跑通。
- **App 的 `SCB->VTOR` 不能写死地址**，要取 `(u32)&__Vectors`（启动文件导出的
  符号）。写死的话跑在 B 槽的固件会把向量表指到 A 槽，中断全部错位，
  而且这种错误只在升级到 B 槽之后才暴露。

## 2. Flash 分区

```
0x08000000 ~ 0x08003FFF   Boot区（16KB，Bootloader + UDS）
0x08004000 ~ 0x0807FFFF   App区（496KB，EdgeMonitor 固件）
```

| 项 | Boot 区 | App 区 |
|----|---------|--------|
| 起始地址 | 0x08000000 | **0x08004000** |
| 大小 | 16KB | 496KB |
| 编译工具 | Keil（独立工程） | Keil（独立工程） |
| 中断向量表 | 默认 | **需重映射（SCB->VTOR）** |

**App 区工程两个必改点**：
1. **链接地址偏移**：Keil → Options → Target → `IROM1` 起始地址 `0x08004000`、大小 `0x7C000`
2. **main() 开头重映射中断向量表**：
   ```c
   SCB->VTOR = 0x08004000;   /* 把中断向量表指到 App 区 */
   ```

## 3. UDS 服务实现（ISO 14229 子集）

### 3.1 CAN 帧映射
| 用途 | 帧 ID | 方向 |
|------|-------|------|
| UDS 请求 | **0x110** | i.MX6ULL → STM32 |
| UDS 响应 | **0x120** | STM32 → i.MX6ULL |

> 用 0x120 做响应 ID，与 App 的 0x100/0x101/0x102 上报 ID 区分，互不干扰。

### 3.2 支持的服务
| SID | 服务 | 请求参数 | 响应 | 说明 |
|-----|------|---------|------|------|
| 0x10 | 会话控制 | Data[1]=0x02(编程) | 0x50 | 进入编程会话 |
| 0x27 | 安全访问 | Data[1]=0x01(请求种子)/0x02(发送密钥) | 0x67 | 种子=0x12345678, 密钥=~种子 |
| 0x31 | 例程控制 | Data[1]=0x01, Data[2]=0xFF, Data[3]=0x00擦除/0x01校验 | 0x71 | 擦除 / CRC 校验 |
| 0x34 | 请求下载 | Data[1..4]=固件长度(大端), Data[5..7]=保留 | 0x74 | 声明升级信息（完整 32 位 CRC32 装不进这 8 字节帧，实际校验放在 0x31，见下） |
| 0x36 | 传输数据 | Data[1]=块序号(0~255循环), Data[2..7]=最多6字节数据 | 0x76 + 回显块序号 | 顺序写 Flash，序号供丢帧重传判断 |
| 0x37 | 退出传输 | 无 | 0x77 | 结束传输 |
| 0x22 | 读 DID | Data[1..2]=DID | 0x62 | 读版本 / A/B 状态 |

**DID 一览**：

| DID | 含义 | 响应体 |
|-----|------|--------|
| `0xF000` | App 软件版本 | `[3][4]` = 主.次版本号 |
| `0xF001` | Bootloader 版本 | `[3][4]` = 主.次版本号 |
| `0xF002` | **A/B 分区状态** | `[3]`=active `[4]`=pending(0xFF 表示无) `[5]`=本次目标槽 `[6]`=已尝试次数 |

`0xF002` 是升级流程的第一步：direct-xip 下两个槽的固件不能互换，上位机必须
先问清楚该传哪一份。老版本 Boot 不认识这个 DID 会返回负响应，`uds_tool`
此时回退到单槽模式（直接用命令行给出的文件），保证新工具还能给旧设备升级。
| 0x11 | ECU 复位 | Data[1]=0x01(硬复位) | 0x51 | 复位跳转 App |

### 3.3 负响应
```
Data[0]=0x7F, Data[1]=请求SID, Data[2]=NRC
```
| NRC | 含义 |
|-----|------|
| 0x13 | 长度错误 |
| 0x22 | 条件不满足（未进入编程会话） |
| 0x31 | 请求超出范围 |
| 0x33 | 安全访问被拒绝 |
| 0x72 | 一般编程失败（Flash 操作失败） |

## 4. 升级完整流程

```
上位机 uds_tool                          STM32 Boot
───────                                    ──────────
1. 上电                      ◄───────     Boot 等待升级握手 3s
2. 0x10 02 编程会话 ────────►  0x50 正响应
3. 0x27 01 请求种子 ────────►  0x67 + 种子
4. 0x27 02 发送密钥 ────────►  0x67 正响应(解锁)
5. 0x31 01 FF 00 擦除 ──────►  0x71 (擦除 App 区)
6. 0x34 固件长度      ───────►  0x74 + 最大块长
7. 0x36 块数据 ×N ──────────►  0x76+块号 (每帧最多6字节写Flash，末块按实际长度收尾；
                                          丢帧/无确认时按原序号重发，同序号收到两次
                                          视为重复帧只重发 ack、不重复写 Flash)
8. 0x37 退出传输 ───────────►  0x77
9. 0x31 01 FF 01 +CRC ──────►  0x71 (校验 App 区 CRC)
10. 0x11 01 复位 ───────────►  跳转 App 运行
```

**失败回退**：任一步负响应/NRC 即停止；CRC 校验失败则不跳转，Boot 停留在升级模式等待重刷。**升级中断不会变砖**（App 区被破坏也不影响 Boot 区）。

## 4.1 升级前状态探测（App 诊断桩，v2.1 补齐）

升级流程假设节点已经停在 Boot 区等待握手。但正常情况下节点大多数时间在跑
App，网关不知道对方现在到底在 Boot 还是 App。之前方案书画过这个探测流程，
但既没有独立的 CAN ID，App 侧也完全没有实现——现在补上：

```
uds_tool                                   STM32 App(若正在跑)
────────                                    ──────────
0x22 读DID(0xF000) ──(CAN ID 0x130)──►     0x62 + 版本号   （证明当前在 App）
0x11 请求复位     ──(CAN ID 0x130)──►     0x51 正响应 → App 内部 NVIC_SystemReset()
                                             │
                                          （复位后 Boot 区重新运行，进入 3 秒握手窗口）
```

- App 只在 `firmware_stm32/app_task.c` 里实现这两个 SID（`handle_diag_frame()`），
  不复用完整的 Boot UDS 状态机，也不支持 0x10/0x27/0x34/0x36——这些只在
  Boot 里处理，App 没必要重复一套。
- 用独立 ID `0x130` 而不是复用 `0x110`，是因为 0x110 已经是"控制命令"帧，
  靠首字节数值范围区分两种协议语义（比如 0x01=LED 和 0x10=会话控制）虽然
  凑巧不会数值冲突，但本质上是把两种不同协议塞进同一个 ID，属于脆弱设计。
- 若探测在 `PROBE_TIMEOUT_MS`（300ms）内没有响应，判定节点已经在 Boot
  等待升级，直接跳过这一步进入正式升级流程；实现见
  `gateway_imx6ull/uds_tool.c` 的 `probe_and_prepare()`。

## 5. 关键实现点

### 5.1 Boot 启动逻辑（超时握手）
```c
main() {
    初始化时钟/延时/CAN;
    等待 3 秒:
        若收到 0x10 02 → 就地回 0x50 正响应，再进入升级模式 break;
    若未升级:
        校验 App 有效(栈顶合法+Reset为Thumb) → JumpToApp();
        否则 停留等待升级（同样要先应答收到的那一帧，再进服务循环）;
    进入 UDS 服务循环;
}
```

> **握手窗口里必须就地应答，这一帧不会再来第二次。**
> 踩过的坑：这里原本只是 `break` 就进服务循环，没有回响应。但那一帧
> 已经被 `HAL_CAN_GetRxMessage` 从 FIFO 取走了，服务循环再也收不到它，
> 于是上位机发出的**第一个** `0x10 02` 永远等不到回复，只能超时退出；
> 而重跑一次时 Boot 已经停在服务循环里（S3 超时 10s 内），那一次就正常了。
> 表现就是"**OTA 第一次必失败、第二次才成功**"，很容易误判成复位后
> 等待时间不够——把 `RESET_WAIT_MS` 从 1s 调到 2s 完全没有用，因为
> 根本不是时序问题，是那一帧被吞了。

### 5.2 Flash 写入（6 字节/帧 + 1 字节块序号，最后补 0xFF 凑半字）
```c
FLASH_Unlock();
// 擦除: 0x31 01 FF 00 → FLASH_ErasePage 循环 0x08004000..0x0807FFFF，步长 FLASH_PAGE_SIZE(2KB)
// 写入: 0x36 → FLASH_ProgramHalfWord(addr, data); addr += 2;（末块不足6字节补0xFF）
FLASH_Lock();
```
- **页大小**：STM32F103ZET6 是高密度器件，Flash 页 2KB，不是 1KB——按错误
  的 1KB 步进擦除不会出错（`FLASH_ErasePage` 按页对齐擦整页），但会把每页
  多擦一次，白白消耗 Flash 擦写寿命，已在 `boot_uds.h` 加 `FLASH_PAGE_SIZE`
  常量修正。
- **末块收尾**：边界检查必须按"本帧实际收到的字节数"而不是固定的
  `BLOCK_LEN(6)` 判断是否超出 `s_dl_total`，否则固件大小不是 6 的整数倍
  （现实中的 .bin 文件基本都是）时，最后一块会被误判越界而拒收，整个
  OTA 流程在最后一步必现失败。
- **块序号 + 重传**：见 3.2 节，Data[1] 专门空出来放块序号，收到重复序号
  只重发 ack、不重复写 Flash，避免重传时对同一 Flash 地址二次编程。

### 5.3 CRC32（软件实现，校验固件完整性）
- 0x34 请求下载时上位机声明固件长度（`s_dl_total`），CRC32 本身留到 0x31 校验步骤单独传（8 字节帧装不下）
- 0x31 01 FF 01 校验时 Boot 按 `s_dl_total`（**实际固件长度，不是整个 496KB App 分区**）重算 CRC32 并比对——
  这里曾经固定按 `APP_SIZE` 扫全区，但上位机的期望 CRC 是只对 .bin 文件本身算的，
  两边范围对不上，只要固件没有刚好写满整个分区就永远校验不过，是原设计里
  "验证脚本" 环节最容易被面试官现场问穿的一处，已改成两边统一按固件实际长度算

### 5.4 跳转 App（关键，注意顺序）
```c
void JumpToApp(void) {
    uint32_t sp = *(volatile uint32_t*)0x08004000;          // App 栈顶
    uint32_t pc = *(volatile uint32_t*)0x08004004;          // Reset_Handler
    if ((sp & 0xFFF00000) != 0x20000000) return;            // 栈顶非法→不跳
    if ((pc & 1) == 0) return;                              // 非Thumb→不跳
    __disable_irq();
    SysTick->CTRL = 0;                                      // 停 SysTick
    SCB->VTOR = 0x08004000;                                 // 向量表指向 App
    __set_MSP(sp);                                          // 设栈指针
    ((void(*)(void))pc)();                                  // 跳转
}
```

## 8. 扩展：完整 ISO-TP（面试可提）

本实现用"每帧 7 字节"简化传输。量产车规版使用 **ISO-TP (ISO 15765-2)**：
- 单帧 SF / 首帧 FF / 连续帧 CF / 流控帧 FC
- 支持最多 4095 字节/消息，连续帧 7~63 字节
- 加传输层状态机 + 超时重传——接口已在 `uds.c` 预留（`block_max` 字段）
- 面试话术：**"当前用简化块传输跑通流程，量产方案可升级为 ISO-TP 连续帧 + 流控，传输层与 UDS 应用层解耦设计"**
