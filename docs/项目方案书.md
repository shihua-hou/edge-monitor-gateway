# 基于 CAN 总线的多传感器远程监控与 OTA 固件升级系统 — 项目方案书（优化版 v2.0）

| 项目名称 | 基于 CAN 总线的多传感器远程监控与 OTA 固件升级系统（EdgeMonitor Gateway） |
|---------|--------------------------------------------------|
| 岗位方向 | 嵌入式软件工程师（车规方向，如禾赛科技） |
| 项目周期 | 约 3~4 周（分 10 阶段，含安全加固） |
| 一句话定位 | 面向园区巡检机器人的移动设备远程运维平台：感知采集 → CAN 总线 → 边缘网关 → 现场/远程双端可视化 → 安全的 CAN OTA 固件升级 |

> **v2.0 变更说明**：本版针对评审出的技术硬伤进行系统性加固——真实传感器数据、安全访问动态种子、传输层可靠性、Web/MQTT 认证、真远程部署、状态探测闭环、烧录防擦除、工程规范与自动化验证。

## 1. 项目概述

### 1.1 背景与动机
嵌入式软件岗位（尤其车规方向）核心考察四块：**MCU 底层驱动、RTOS、CAN 总线通信、Bootloader/UDS 远程升级**。本项目以一套真实可演示的完整系统，一次性覆盖全部四项能力，而不是零散的 demo。

### 1.2 核心价值：三闭环
| 闭环 | 链路 | 覆盖技术点 |
|------|------|-----------|
| ① 数据上行 | 传感器 → STM32 → CAN → i.MX6ULL 网关 → (本地Qt + MQTT) → Web | MCU驱动、FreeRTOS、CAN、SocketCAN、MQTT |
| ② 控制下行 | Web 按钮 → MQTT → 网关 → CAN → STM32 → 执行设备 → 状态回传 | 全链路控制、编码器闭环 |
| ③ **固件升级** | Web 上传 .bin → 网关 UDS 上位机 → CAN → STM32 Bootloader → 写 Flash → 校验 → 跳转 | **Bootloader、UDS、IAP、动态安全访问、CRC、OTA** |

### 1.3 应用场景与设计动机
本项目面向**园区巡检机器人**应用：

| 设计点 | 动机与说明 |
|--------|-----------|
| 小车 = 移动平台 | 园区/厂区环境巡检载体（当前 R3X 底盘仅作**验证模型**，后续更换承重更大的车体） |
| 传感器 = 环境感知 | 采集温度/湿度/光照/障碍距离/姿态，完成巡检数据记录 |
| GPS + 摄像头 | 巡检定位 + 现场画面回传 |
| **双端显示** | 本地 7 寸屏供**现场**巡检人员即时查看/控制（低延迟）；Web 端供**远程中控室/手机**多路监控（可扩展多车接入） |
| **OTA 动机** | 巡检设备分散部署，免到现场拆机即可升级固件——设备运维刚需 |

### 1.4 版本演进规划（体现原型→量产工程思维）
| 版本 | 内容 |
|------|------|
| **V1 原型（当前）** | R3X 底盘验证 + 有线 CAN 台架联调 + 监控/控制/OTA 全闭环 + 安全加固 |
| **V2 自供电** | 太阳能发电板 + MPPT 充电控制 + 锂电池自供电，主控上车，功耗预算见 3.5 |
| **V3 量产化** | 承重更大车体 + 无线网关扩展 + 多车接入 + A/B 分区 OTA 可靠升级 + ISO-TP 完整传输层 |

## 2. 系统架构

### 2.1 总体架构图
```
  感知/执行层                    边缘网关层                      远程应用层
┌─────────────────┐   CAN(500K)  ┌──────────────────────────┐   WiFi   ┌──────────┐
│ 战舰STM32F103    │◄───────────►│ i.MX6ULL                 │◄────────►│ 路由器     │
│ ├ 超声波/MPU6050 │  CANH/CANL  │ ├ 7寸RGB屏(Qt本地可视化)  │   ┌─────►│  (本地)   │
│ │ DHT11/光敏     │  GND(共地)  │ ├ USB摄像头(自写V4L2推流)│   │      └────┬─────┘
│ ├ LED/蜂鸣器     │             │ ├ USB WiFi                │   │           │
│ ├ TB6612+MG513   │  Boot区:    │ ├ GPS(UART/NMEA解析)      │   │   MQTT(TLS/认证)
│ │  编码器小车    │  UDS+Flash  │ └ 网关程序(C: CAN/MQTT)   │   │           ▼
│ └ 12V电池(独立)  │  App区:监控 │   ▲          │ frp/云broker └──►│ 远程Web/手机  │
└─────────────────┘             └───┼──────────┘              └──────────┘
                                     └ 本地数据中枢(网关持有,Qt与Web统一取数)
```

### 2.2 分层职责
| 层 | 职责 | 关键实现 |
|----|------|---------|
| 感知/执行层 | 多传感器采集、执行设备控制、Bootloader 接收升级 | STM32F103 + FreeRTOS + CAN |
| 边缘网关层 | CAN 桥接、数据聚合、本地屏、自写V4L2视频、MQTT(带认证)、UDS 上位机 | i.MX6ULL Linux + C 网关 |
| 远程应用层 | 仪表盘可视化、远程控制、地图定位、OTA 升级界面（登录鉴权） | Web(HTML/JS) + MQTT WebSocket(TLS) |

### 2.3 三条链路数据流
```
上行: STM32采集 → CAN帧 → SocketCAN → 网关解析 → 本地Qt显示 / MQTT发布(认证) → Web
下行: Web按钮(登录) → MQTT → 网关 → CAN帧 → STM32 → 执行设备 → 状态字回传确认
升级: Web登录上传bin → 状态探测(0x10/0x22) → 网关分块 → UDS(CAN,动态安全) → Boot写Flash → CRC校验 → 跳转App
```

## 4. 软件方案

### 4.1 STM32 固件（FreeRTOS + HAL库）

> v2.1 变更：正点原子现在的战舰V4资料包已经不再提供标准库(StdPeriph)例程，
> 只有寄存器版本和 HAL 库版本，所以 App 侧改为基于官方 HAL 版 FreeRTOS 例程
> 开发（`can.c`/`app_task.c`/`sensor/` 已全部改完）。Boot 侧（`bootloader/`）
> 暂时保留标准库写法，是独立的第二个 Keil 工程，做 OTA 阶段再一起改成 HAL。

**任务模型与栈分配（防栈溢出）**：
| 任务 | 优先级 | 栈 | 周期 | 说明 |
|------|--------|----|------|------|
| Sensor 采集 | 3 | 512 字 | 见调度表 | 分时采集，**不打印浮点** |
| CAN 上报 | 2 | 256 字 | 1Hz/5Hz | 从队列取数据组帧发送 |
| Cmd 处理 | 2 | 256 字 | 阻塞 | 接收 0x110/0x111，队列隔离 |
- `configTOTAL_HEAP_SIZE ≥ 20KB`；浮点打印禁用（数据用整数/定点上报，调试串口单独处理）

**传感器采集调度表（真实时序，杜绝"读不到"）**：
| 传感器 | 周期 | 采集方式 | 说明 |
|--------|------|---------|------|
| DHT11 | 1000ms | 单总线 | **最小采样间隔 1s，采集任务必须遵守** |
| 超声波 | 200ms | TIM4 输入捕获 | 连续测距间隔 ≥ 60ms |
| MPU6050 | 20ms | 软件 I2C (PB10/PB11) | 姿态解算（简单互补滤波） |
| 光敏 | 200ms | ADC1_CH1 | 中断/DMA 采样 |

- **本版明确要求：传感器驱动必须是真实驱动，禁止假数据**。DHT11/超声波/光敏从正点原子战舰例程移植，MPU6050 用软件 I2C 例程。

- **App 区**（EdgeMonitor 固件）：上述 3 任务
- **Boot 区**（Bootloader + UDS，见 4.4）
- 工程：正点原子战舰 FreeRTOS 例程 + 自写 can.c/app_task.c

### 4.2 CAN 通信协议（STM32 ↔ i.MX6ULL）
- 波特率 **500Kbps**（APB1=36MHz, Prescaler=4, BS1=9, BS2=8）
- 标准帧，8 字节数据

| 帧 ID | 方向 | 含义 |
|-------|------|------|
| 0x100 | STM32→网关 | 状态上报（温度/光照/距离/状态字） |
| 0x101 | STM32→网关 | IMU 姿态（俯仰/横滚/偏航） |
| 0x102 | STM32→网关 | 小车运动状态（左右轮转速/里程） |
| 0x110 | 网关→STM32 | 控制命令（设备/动作/参数） |
| 0x111 | 网关→STM32 | 参数配置（上报周期/阈值） |
| 0x130 | 网关→STM32 | **App 诊断请求（升级前状态探测，仅 0x22/0x11，v2.1 新增，不占用 0x110）** |
| 0x120 | STM32→网关 | **诊断响应（Boot 的 UDS 应答与 App 的 0x130 诊断应答共用）** |

**上报节流**：网关无远程订阅时，STM32 降频（1Hz）；有订阅时按配置周期（5Hz）——避免无效总线占用。

### 4.3 i.MX6ULL 网关（Linux + C）
| 模块 | 实现 |
|------|------|
| CAN 接入 | SocketCAN（can0，500K） |
| 网关程序 | C 多线程：CAN 接收解析 + 数据聚合 + 本地TCP/MQTT 发布 + UDS 上位机 |
| 本地屏 | Qt（交叉编译，`-platform linuxfb`），与 Web 统一数据源 |
| MQTT | mosquitto broker（开 1883 + 8083 WebSocket）**+ 用户名/密码认证，禁用匿名** |
| 视频 | **自写 V4L2 采集 + HTTP/MJPEG 推流**（UVC 硬件 MJPEG → mmap 采集 → 多客户端 HTTP 推流，**带 token 鉴权**，不走 MQTT） |
| GPS | 网关程序自解析 NMEA（$GPGGA/$GPRMC）提经纬度 |
| Web 服务 | python3 http.server / nginx（**登录鉴权**） |

### 4.4 Bootloader / UDS（核心亮点，v2 安全加固版）

**Flash 分区**：
```
0x08000000 ~ 0x08003FFF  Boot区(Bootloader+UDS, 16KB)
0x08004000 ~ 0x0807FFFF  App区(EdgeMonitor固件, 496KB)
```

**UDS 诊断服务（ISO 14229 子集）**：
| SID | 服务 | 用途 |
|-----|------|------|
| 0x10 | 会话控制 | 进入编程会话（**含 S3 超时退出**） |
| 0x27 | 安全访问 | **动态种子 + 非线性密钥算法**（见下） |
| 0x31 | 例程控制 | 擦除 Flash / CRC 校验 |
| 0x34 | 请求下载 | 声明固件大小/起始地址 |
| 0x36 | 传输数据 | **分块传输 + 块序号 + 确认/重传**（见下） |
| 0x37 | 请求退出传输 | 结束传输 |
| 0x22 | 读 DID | 读版本/序列号（**用于升级前状态探测**） |
| 0x11 | ECU 复位 | 跳转 App |

**v2 安全加固——0x27 动态种子**：
- 种子**不再写死**：`seed = RESET_COUNTER ^ 0xA5A5 ^ (FLASH_SIZE >> 2)`，RESET_COUNTER 每次复位 +1 存备份寄存器（每次会话都不同）
- 密钥算法：**XTEA 加密**（固定 128-bit key），替换原来的 `~seed`
- 目的：种子每次会话都不同，避免重放同一把"密钥"；比固定种子/`~seed`这种
  一眼就能看穿的算法有意义的提升
- **诚实说明**：密钥是编译期常量，和固件/上位机源码一起放在同一个仓库里。
  只要仓库开源（本项目工程规范里明确要放 GitHub），这把"密钥"就是公开的，
  XTEA 本身也是公开算法——所以"算法不可直读"这个说法在开源之后不成立，
  面试时应该讲成"演示了动态种子挑战-应答机制和对称加密算法的接线方式，
  量产车规方案密钥要放 HSM/安全芯片，不能编译进固件"，而不是声称做到了
  真正的机密性

**v2.1 可靠性加固——0x36 传输层**：
- 数据帧携带**块序号**（0~255 循环），载荷 6 字节（Data[1]=序号 占掉了 1 字节，
  之前"v2"版本写着有块序号但 8 字节全用来装数据，其实根本没地方放序号，
  是文档先行、代码没跟上的一处；现已按真实帧格式改成 6 字节数据 + 1 字节序号）
- 每帧响应带当前块号，上位机校验连续性：**同一块连续 3 次无确认 → abort，
  提示用户重跑升级工具**（不做跨进程的自动断点续传——一次性传输脚本重启
  成本很低，没必要为此再加一层状态持久化）
- 整包结束后 0x31 校验 CRC，失败则**回退 Boot 等待重刷**（不损坏现有 App）
- 0x10 编程会话 **S3 超时（10s 无诊断请求）自动退出**回 Boot 等待——上位机崩溃不卡死
- V3 升级为完整 ISO-TP 传输层（连续帧/流控）

**v2.1 升级前状态探测（独立诊断 ID，网关统一处理）**：
```
网关发 0x22 0xF000(读App版本)  ——CAN ID 0x130（App 诊断桩专用，不占 0x110）——
  ├─ 收到版本号 → 当前在 App → 发 0x11 请求复位(同一 ID) → App 内部 NVIC_SystemReset()
  │                              → Boot 重新起来，进入 3 秒握手窗口 → 再走正式升级流程
  └─ 短超时(300ms)无响应 → 已在 Boot 等待升级 → 直接进入正式升级流程
```
- App 只实现 0x22/0x11 两个最小诊断服务（`app_task.c` 的 `handle_diag_frame()`），
  监听独立 ID `0x130`，不占用控制命令用的 `0x110`；Boot 区仍固定用
  `0x110`(请求)/`0x120`(响应)，两者运行时间不重叠，互不影响
- `0x10/0x27/0x31/0x34/0x36` 只有 Boot 处理，App 不实现完整 UDS 状态机
- 探测逻辑实现见 `gateway_imx6ull/uds_tool.c` 的 `probe_and_prepare()`

**烧录防擦除（关键坑规避）**：
- **优先 ST-Link + Keil 分工程烧录**：Boot 工程 → 0x08000000；App 工程 → 0x08004000，**Flash 配置不勾选"全片擦除"**，避免串口 ISP 擦掉 Boot
- ISP 方式：明确警告"ISP 默认全片擦除会抹掉 Boot"，需先备份/重烧 Boot
- App 工程两必改点：Keil IROM1=0x08004000/0x7C000；main 开头 `SCB->VTOR=0x08004000`

### 4.5 远程部署与安全（v2 新增）

**"真远程"双模式**：
| 模式 | 实现 | 适用 |
|------|------|------|
| A 本地演示 | broker 在 i.MX6ULL，局域网访问 | V1 演示/联调 |
| B **真远程** | 云 VPS 部署 EMQX/Mosquitto（公网），或 **frp 内网穿透**把 1883/8083/视频端口映射到公网 | V2 起，体现"远程运维" |

**安全清单（Web/MQTT/视频统一收紧）**：
1. broker 禁匿名：`allow_anonymous false`，设备凭据连接
2. **broker ACL**（v2.1 补齐）：`allow_anonymous false` 只做认证，不代表授权——不开
   ACL 时任何认证账号（包括本该只读的 viewer）都能往 `monitor/cmd` 发控制命令。
   已提供 `gateway_imx6ull/acl.example` 模板，把只读账号真正限制成只读；默认没有
   随配置一起启用，因为直接在 `mosquitto.conf` 里打开 `acl_file` 却不提供对应文件
   会导致 broker 启动失败，需要手动 `cp` 一份再取消注释
3. Web 登录鉴权：登录页 → MQTT connect 带 username/password，网关侧对 `monitor/cmd`
   的内容做取值范围校验（见 `gateway_mqtt.c`），不再无脑透传
4. 视频 MJPEG 服务带 token（URL 参数），**v2.1 起 token 不再是登录密码明文**，
   而是浏览器端 `SHA-256(用户名:密码)` 取前 16 位十六进制——避免密码出现在
   URL 里被浏览器历史/代理日志/Referer 头记下来
5. MQTT 建议走 TLS：`mosquitto.conf` 预留了 8084 TLS listener，Web 端在
   `https:` 页面下会自动切换到 `wss://`，本地台架联调仍走明文 `ws://`

### 4.6 Web 端
- 登录页 + mqtt.js 通过 `wss://板子IP:8084`（页面走 https 时自动启用）或
  `ws://板子IP:8083`（局域网联调）连接（带凭据）
- 页面：数据仪表盘（实时曲线/数值）+ 控制面板 + Leaflet 地图（GPS 打点）+ 视频流（`<img>` 引自写 MJPEG 推流服务）+ **OTA 升级页（选 .bin → 进度条 → 结果反馈）**

## 5. 关键技术点与岗位契合

| 技术点 | 具体体现 | 对应岗位需求 |
|--------|---------|-------------|
| MCU 外设驱动 | 超声波/MPU6050/DHT11/ADC/PWM/编码器（**真实驱动**） | 禾赛 JD：MCU 外设驱动 |
| RTOS | FreeRTOS 多任务 + 队列中断模型 + 栈/堆规划 | 禾赛 JD：RTOS |
| CAN | 自研协议栈 + SocketCAN + 500K 联调 + 上报节流 | 禾赛 JD：CAN |
| **Bootloader/UDS** | IAP 分区 + ISO14229(UDS子集) + **动态安全访问** + 传输可靠 + CRC + 失败回退 + OTA | **禾赛 JD：Bootloader/UDS** |
| 嵌入式 Linux | 交叉编译 + SocketCAN + 系统移植 | 嵌入式软件综合能力 |
| **Linux 视频接口** | **自写 V4L2 采集 + mmap + HTTP/MJPEG 推流**（替代现成工具） | 驱动接口级能力（加分项） |
| 网络/全栈 | MQTT(认证) + Web(登录) + 视频流(token) + 地图 + 真远程部署 | 差异化亮点（物联网全栈） |
| 安全 | 动态种子安全访问、broker 认证、Web 鉴权、视频 token | 工程素养 + 安全意识 |
| 可靠性 | 发送超时处理、CRC 校验、升级失败回退、S3 会话超时、烧录防擦除 | 工程素养 |

**面试话术要点**：
1. 强调"三闭环"：数据、控制、升级——不是单点 demo，是完整系统
2. 强调"协议先行 + 状态探测"：升级前先探测节点状态，协议有完整闭环
3. 强调"安全不是摆设，也不假装万无一失"：0x27 动态种子、broker 认证+ACL、Web 鉴权、
   视频 token 都做了，同时能讲清楚哪些是简化（密钥编译进固件、没有 HSM）、
   量产车规方案该怎么补——这种边界感比"我全做对了"更能体现 ISO 21434 的安全意识
4. 强调"可靠性设计"：S3 超时、传输确认重传、失败回退、烧录防擦除
5. 强调"全链路问题排查"：从传感器到 Web 每一层的调试经验

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| CAN 不通 | 检查波特率一致、共地、120Ω 终端电阻；candump 排查 |
| i.MX6ULL USB 供电不足 | 带电源 USB HUB |
| 出厂 Buildroot 无 apt/gcc | 烧正点原子 Ubuntu 镜像，或全交叉编译 |
| 小车 CAN 线随动缠绕 | 台架小范围演示；V3 扩展 nRF24L01/ESP8266 无线 |
| **传感器读数异常/读取超时** | DHT11 遵守 1s 间隔；逐个例程验证；引脚冲突已规避 |
| **任务栈溢出/随机死机** | 按 4.1 栈分配；禁浮点打印；FreeRTOS 栈监测钩子 |
| **OTA 传输丢帧** | 块序号 + 确认重传 + S3 超时 + 失败回退（v2 已设计） |
| **烧录抹掉 Boot** | ST-Link 分工程烧录，不勾选全片擦除；ISP 方式有警告 |
| **Web 被未授权控制** | broker 禁匿名 + Web 登录 + 控制 topic 校验 |
| Qt 交叉编译环境复杂 | 按正点原子资料包教程搭建；或 Ubuntu 系统 apt 装 Qt |
